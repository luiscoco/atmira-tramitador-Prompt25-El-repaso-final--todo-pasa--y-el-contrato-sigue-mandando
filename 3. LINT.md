# ESLint en `tramitador` — flat config única para todo el monorepo

Tercer paso (los anteriores: [MONOREPO.md](MONOREPO.md) y [TYPESCRIPT.md](TYPESCRIPT.md)).
Sigue sin haber una línea de código de aplicación: aquí se decide **qué se revisa y qué no**.

## Qué hay

```
eslint.config.js               (raíz, flat config ESLint 9 — no hay .eslintrc en ningún sitio)
package.json                   -> scripts.lint = "eslint ."
```

Una sola config en la raíz, igual que con `tsconfig.base.json`: las reglas se deciden una
vez y ningún workspace las relaja por su cuenta. La diferencia con TypeScript es que aquí
ni siquiera hay herencia — ESLint 9 sube buscando `eslint.config.js` desde el fichero
linteado, encuentra el de la raíz y lo aplica a los tres workspaces.

El fichero es ESM (`import` / `export default`) sin ningún truco: la raíz ya declara
`"type": "module"`, así que un `.js` es un módulo.

## Los pasos que se siguieron

### 1. Instalar lo que faltaba

El repo no tenía **ninguna** dependencia real todavía (solo los tres symlinks entre
workspaces), así que el script no habría arrancado. Desde la raíz:

```bash
npm i -D eslint @eslint/js typescript-eslint typescript
```

- `@eslint/js` trae `js.configs.recommended`. Va aparte del paquete `eslint` desde la v9.
- `typescript-eslint` es el paquete **unificado** de la v8: reemplaza al par
  `@typescript-eslint/parser` + `@typescript-eslint/eslint-plugin` de la era `.eslintrc`.
  Exporta el parser, el plugin, los presets y el helper `config()` en un solo sitio.
- `typescript` es peer dependency de `typescript-eslint`. Hacía falta igualmente para el
  paso anterior, donde se dio por instalado sin estarlo.

### 2. Escribir `eslint.config.js`

Tres decisiones, una por bloque.

**Bloque de ignores.** Un objeto con `ignores` y **nada más** — sin `files`, sin `rules`:

```js
{ ignores: ['**/dist/**', '**/node_modules/**', '**/.turbo/**', '**/*.gen.ts'] }
```

Esa forma "solo-ignores" es lo que en flat config convierte los patrones en **globales de
toda la ejecución**. Si el mismo `ignores` se pusiera dentro del bloque que tiene `files` y
`rules`, solo excluiría ficheros de *ese* bloque, que no es lo que se quiere.

Los `**/` del principio no son decorativos: sin ellos, `dist/**` solo taparía el `dist/` de
la raíz, no `apps/backend/dist/`. En un monorepo cada workspace tiene el suyo.

`**/*.gen.ts` es el que importa de verdad. Van a ser los tipos generados desde el contrato
OpenAPI: se regeneran a cada cambio del contrato y nadie los toca a mano, así que un error
de lint ahí no es accionable — o lo arregla el generador, o no se arregla.

**Bloque de reglas.** Acotado a TypeScript con `files`, y extendiendo los dos presets:

```js
{
  files: ['**/*.{ts,tsx}'],
  extends: [js.configs.recommended, ...tseslint.configs.recommended],
  rules: { /* … */ }
}
```

El `extends` **dentro** de un objeto de config no es flat config estándar — es azúcar que
aporta el helper `tseslint.config()` que envuelve todo el fichero. Por eso se usa: sin él
habría que esparcir los presets al nivel superior del array, y entonces se aplicarían a
todo el árbol en vez de solo a `.ts` / `.tsx`. Es justo lo que se pidió evitar.

**La regla de las variables sin usar.** El contrato con el prefijo `_`:

```js
'no-unused-vars': 'off',
'@typescript-eslint/no-unused-vars': ['error', {
  argsIgnorePattern: '^_',
  varsIgnorePattern: '^_',
  caughtErrorsIgnorePattern: '^_',
  destructuredArrayIgnorePattern: '^_',
  args: 'after-used',
  caughtErrors: 'all',
  ignoreRestSiblings: true,
}]
```

Los cuatro patrones cubren los cuatro sitios donde puede aparecer un símbolo muerto, que
son opciones independientes entre sí:

| Opción | Qué tapa |
|---|---|
| `argsIgnorePattern` | `(_req, res) => …` — el parámetro que impone una firma ajena |
| `varsIgnorePattern` | `const _loQueSea = …` y los imports sin usar |
| `caughtErrorsIgnorePattern` | `catch (_e) { … }` |
| `destructuredArrayIgnorePattern` | `const [, _b, c] = tupla` |

Esto es deliberadamente **el mismo idioma que ya usa `tsconfig.base.json`**: el `_` como
"no usado a propósito" viene de `noUnusedLocals` / `noUnusedParameters`
([TYPESCRIPT.md](TYPESCRIPT.md)). Si ESLint usara otro convenio, el mismo fichero pasaría
un chequeo y fallaría el otro.

Las tres opciones de abajo son las que evitan falsos positivos:

- `args: 'after-used'` — solo se queja del parámetro sin usar si **después** hay alguno que
  sí se usa. En `(a, b, c)` con solo `c` usado, `a` y `b` son obligatorios para poder llegar
  a `c`: exigir `_a`, `_b` sería ruido.
- `caughtErrors: 'all'` — en la v8 de typescript-eslint ya es el valor por defecto; se deja
  escrito porque cambió respecto a la v7 y es mejor no depender de la versión instalada.
- `ignoreRestSiblings: true` — hace que `const { password, ...resto } = user` no marque
  `password`. Omitir una propiedad por destructuring es justo para lo que se escribe.

La base `no-unused-vars` se apaga explícitamente. `tseslint.configs.recommended` ya la apaga
por su cuenta (vía `eslint-recommended`) para que no duplique errores con la versión TS, pero
dejarlo escrito documenta la intención y protege si algún día se lintan `.js`.

### 3. Añadir el script

```json
"scripts": { "lint": "eslint ." }
```

El `.` es el directorio, no un glob: ESLint 9 recorre desde ahí y decide qué lintar cruzando
los `files` de la config con los `ignores` globales.

## Cómo verificar

Lo importante: un lint que pasa **no prueba nada** cuando aún no hay código. Puede estar
pasando porque las reglas funcionan o porque no está mirando ningún fichero. Así que la
comprobación se hizo con ficheros sonda temporales, ya borrados.

### 1. La regla del `_`

Con un fichero que mezcla los cuatro casos:

```ts
export function handler(_req: string, res: string, extra: number): string {
  const _unused = 1;
  const usado = 2;
  try { JSON.parse(res); } catch (_e) { /* ignorado */ }
  return `${usado}`;
}
```

```
packages/contrato/src/__probe.ts
  1:52  error  'extra' is defined but never used. Allowed unused args must match /^_/u
```

Un único error, y en el sitio correcto: `extra` no lleva prefijo. `_req`, `_unused` y `_e`
pasan limpios. El propio mensaje confirma qué patrón se está aplicando.

### 2. Los ignores

```bash
npx eslint packages/contrato/src/__probe.gen.ts
npx eslint apps/backend/dist/__probe.ts
```

Los dos responden lo mismo:

```
0:0  warning  File ignored because of a matching ignore pattern.
```

Pedir explícitamente un fichero ignorado y que ESLint avise es la señal de que el patrón
casa. Pero eso solo demuestra que *no lo mira*, no que hubiera algo que ver. La prueba que
cierra el círculo es la negativa — el mismo `.gen.ts`, saltándose los ignores:

```bash
npx eslint --no-ignore packages/contrato/src/__probe.gen.ts
```

```
1:22  error  Unexpected any. Specify a different type       @typescript-eslint/no-explicit-any
2:7   error  'noUsado' is assigned a value but never used.  @typescript-eslint/no-unused-vars
```

Dos errores reales. O sea: el silencio del comando anterior venía del `ignores`, no de que
las reglas no llegaran a aplicarse. Sin este paso, un `files` mal escrito daría el mismo
"todo bien" tranquilizador.

### 3. El estado limpio

Borradas las sondas:

```bash
npm run lint     # exit 0
```

## Detalles a tener en cuenta

**Los `.js` se recorren pero no se revisan.** `eslint .` incluye los `.js` / `.mjs` / `.cjs`
por defecto —el propio `eslint.config.js` entre ellos—, pero como ningún bloque les asigna
reglas, pasan sin nada. Es inofensivo hoy porque no hay JS de aplicación. Si algún día lo
hay, hace falta un bloque propio con `files: ['**/*.js']`; no basta con suponer que el de
TypeScript los cubre.

**No hay type-aware linting.** `tseslint.configs.recommended` es el preset que funciona solo
con el AST, sin pedirle tipos al compilador. Las reglas más potentes
(`no-floating-promises`, `no-misused-promises`, `await-thenable`) viven en
`recommendedTypeChecked` y exigen `languageOptions.parserOptions.projectService: true`. Eso
encarece cada ejecución y obliga a que todo fichero linteado esté dentro de algún `tsconfig`
— con `packages/contrato` todavía sin el suyo, es un paso para cuando haya código. Es el
siguiente escalón natural de este fichero.

**`js.configs.recommended` acotado a `.ts` es lo que se pidió, y tiene un matiz.** Buena
parte de lo que aporta (`no-undef`, por ejemplo) es redundante con el compilador de
TypeScript; de hecho `tseslint` desactiva varias a propósito para evitar falsos positivos en
sintaxis TS. Lo que queda útil son las de lógica pura: `no-constant-condition`,
`no-dupe-keys`, `no-unreachable`.

**Nada de formato.** Aquí no hay Prettier ni reglas de estilo, y es deliberado: ESLint revisa
lógica, el formato es otra herramienta. Si se añade Prettier, lo que corresponde es
`eslint-config-prettier` al **final** del array para apagar cualquier regla que compita, no
mezclar los dos trabajos en una sola pasada.

**Falta engancharlo a CI y a los workspaces.** Hoy `npm run lint` solo existe en la raíz y
solo se ejecuta a mano. Cuando entre Turborepo —el `.turbo/` ya está en los ignores— lo suyo
es una task `lint` que cachee por workspace.
