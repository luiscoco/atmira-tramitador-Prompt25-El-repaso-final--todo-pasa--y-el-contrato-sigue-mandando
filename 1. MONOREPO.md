# Monorepo `tramitador` — estructura y verificación del enlace entre paquetes

Estructura creada y verificada con un `npm install` real.

## Qué hay

```
package.json                   (raíz, private, workspaces)
.gitignore
apps/backend/package.json      -> @tramitador/backend
apps/frontend/package.json     -> @tramitador/frontend
packages/contrato/package.json -> @tramitador/contrato
package-lock.json              (generado; sí debe versionarse)
```

- **Raíz**: `package.json` con `"private": true`, `"type": "module"` y `"workspaces": ["apps/*", "packages/*"]`.
- Los cuatro `package.json` llevan `"type": "module"` (ESM puro).
- `apps/backend/package.json` y `apps/frontend/package.json` declaran `"@tramitador/contrato": "*"`. Llevan además `"private": true` para que nunca se publiquen por accidente; `packages/contrato` se dejó publicable por si algún día se quiere subir a un registro.
- **Cero dependencias de negocio**: `npm install` solo creó enlaces, no descargó nada del registro.

### Sobre `"*"` vs `workspace:*`

npm resuelve `"*"` contra los workspaces locales **antes** de mirar el registro, así que es el idioma nativo de npm workspaces. `workspace:*` es de pnpm/yarn; npm lo tolera pero no hace falta. Aquí se usa `"*"`.

## Cómo verificar el enlace

### 1. Instala desde la raíz

Siempre desde la raíz, nunca dentro de un workspace:

```bash
npm install
```

Salida obtenida: `added 3 packages, and audited 7 packages`. Esos 3 "paquetes" son los tres symlinks, no descargas.

### 2. Mira el árbol

```bash
npm ls --all
```

```
tramitador@0.0.0
+-- @tramitador/backend@0.0.0 -> .\apps\backend
| `-- @tramitador/contrato@0.0.0 deduped -> .\packages\contrato
+-- @tramitador/contrato@0.0.0 -> .\packages\contrato
`-- @tramitador/frontend@0.0.0 -> .\apps\frontend
  `-- @tramitador/contrato@0.0.0 deduped -> .\packages\contrato
```

La flecha `->` apuntando a una ruta relativa local es la señal definitiva: está **enlazado**, no instalado desde un registro. Si estuviera resolviéndose del registro verías `@tramitador/contrato@1.2.3` sin flecha (y en realidad fallaría con `404 Not Found`, porque ese nombre no existe en npmjs).

### 3. Comprueba los symlinks en disco

```bash
ls -la node_modules/@tramitador     # bash
```

```powershell
Get-ChildItem node_modules\@tramitador | Select-Object Name, LinkType, Target   # PowerShell
```

Los tres aparecen como enlaces a `apps/backend`, `apps/frontend` y `packages/contrato`.

### 4. Prueba la resolución real de Node

Lo más concluyente — que el runtime encuentre el paquete desde cada app:

```bash
node --input-type=module -e "
import { createRequire } from 'node:module';
import { pathToFileURL } from 'node:url';
import { resolve } from 'node:path';
const r = createRequire(pathToFileURL(resolve('apps/backend/index.js')));
console.log(r.resolve('@tramitador/contrato/package.json'));
"
```

Devuelve `...\packages\contrato\package.json` desde backend y desde frontend. Es decir, ambos ven el código fuente local.

### 5. Comprobación negativa (opcional)

La más tranquilizadora: busca en `package-lock.json` que la entrada de contrato sea un `"link": true` / `"resolved": "packages/contrato"` y **no** una URL de `registry.npmjs.org`:

```bash
grep -n "contrato" -A3 package-lock.json
```

## Detalle a tener en cuenta

`packages/contrato` aún no tiene `main` ni `exports`, así que `import '@tramitador/contrato'` (sin subruta) todavía falla — es esperado con un paquete vacío. En cuanto se le añada el punto de entrada, lo natural en ESM es:

```json
{ "exports": { ".": "./src/index.js" } }
```

Y no hará falta reinstalar: el symlink ya apunta al directorio, los cambios se ven al instante. Solo hay que volver a ejecutar `npm install` desde la raíz al añadir o cambiar dependencias.
