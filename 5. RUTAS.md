# Rutas en `tramitador` — las siete operaciones del contrato

Segundo paso del contrato (el anterior: [CONTRATO.md](CONTRATO.md)). Allí se fijó el
**vocabulario** — qué es una solicitud, qué estados tiene — con `paths: {}` vacío.
Aquí se fija la **superficie**: qué se le puede pedir a la API, con qué parámetros
y, sobre todo, **con qué puede responder cuando algo va mal**.

Sigue sin haber una línea de backend. El objetivo del paso es que los códigos de
error se decidan una vez, en el contrato, y no los vaya improvisando cada
`if` del servidor.

## Qué hay

```
packages/contrato/openapi.yaml   -> OpenAPI 3.0.3: servers + paths + components
```

Siete operaciones, todas bajo el servidor `/api`:

| Método | Ruta | `operationId` | Respuestas |
| --- | --- | --- | --- |
| GET | `/salud` | `obtenerSalud` | 200, 500 |
| GET | `/tipos` | `listarTipos` | 200, 500 |
| GET | `/operadores` | `listarOperadores` | 200, 500 |
| GET | `/solicitudes` | `listarSolicitudes` | 200, 400, 500 |
| POST | `/solicitudes` | `crearSolicitud` | 201, 400, 500 |
| GET | `/solicitudes/{id}` | `obtenerSolicitud` | 200, 400, 404, 500 |
| POST | `/solicitudes/{id}/transiciones` | `aplicarTransicion` | 200, 400, 404, 409, 500 |

Y tres bloques nuevos de `components` que antes no existían:

```
components/parameters   -> IdSolicitud, FiltroEstado
components/responses    -> SolicitudNoEncontrada, IdMalFormado, ErrorInterno
components/schemas      -> los ocho de CONTRATO.md, sin tocar
```

Ningún esquema cambió en este paso. Lo único que se modificó fuera de `paths` fue
la frase de `info.description` que decía "las rutas se definirán más adelante".

## Los pasos que se siguieron

### 1. Leer el contrato entero antes de tocarlo

Los esquemas ya estaban escritos y el paso consistía en **conectarlos**, no en
reinventarlos. De esa lectura salieron tres restricciones que condicionan todo lo
demás:

- `Solicitud.id` es `format: uuid`, pero `referencia` es el código legible
  (`SOL-2026-0007`). [CONTRATO.md](CONTRATO.md) dejaba abierto cuál va en la URL.
- `Error` solo tiene `mensaje` y `detalle`. **No hay `codigo`**, así que el
  contrato no puede distinguir por máquina un 400 de otro 400.
- `Accion` admite los tres verbos siempre. Las transiciones inválidas no las
  puede impedir el esquema — solo puede describirlas el **código de respuesta**.

### 2. Añadir `servers` antes que `paths`

```yaml
servers:
  - url: /api
```

Una URL relativa, no `https://algo/api`. Con una relativa el documento sirve igual
en local, en preproducción y en producción: el cliente la resuelve contra el
origen desde el que se sirve. Poner ahí un host concreto habría obligado a
mantener una lista de entornos en el contrato.

Esto además cierra el único **error** que [CONTRATO.md](CONTRATO.md) dejaba
pendiente en el `lint` (`no-empty-servers`).

### 3. Escribir las operaciones de lectura simple

`/salud`, `/tipos` y `/operadores` no tienen parámetros ni cuerpo. La única
decisión real fue **qué NO es un error**:

> Una lista vacía es un `200` con `[]`, no un `404`.

Parece obvio y se incumple constantemente. Está escrito en la `description` de
las tres, porque es el tipo de cosa que el contrato debe decidir para que backend
y frontend no discrepen.

`/salud` devuelve `{ ok: boolean }` con un esquema **inline**, no un componente.
Es el único sitio donde aparece esa forma; extraerlo a `components/schemas` habría
añadido un nombre al vocabulario del dominio para algo que no es dominio.

### 4. Extraer los parámetros y errores repetidos

Antes de escribir las rutas con `{id}` se sacaron a `components` las piezas que
iban a repetirse. `id` aparece en dos rutas y los errores de "no existe" e
"interno" en casi todas:

```yaml
components:
  parameters:
    IdSolicitud:      # name: id, in: path, required: true, format: uuid
    FiltroEstado:     # name: estado, in: query, required: false
  responses:
    SolicitudNoEncontrada:   # 404
    IdMalFormado:            # 400
    ErrorInterno:            # 500
```

El `id` se declara **a nivel de path**, no dentro de cada operación:

```yaml
/solicitudes/{id}:
  parameters:
    - $ref: '#/components/parameters/IdSolicitud'
  get:
    ...
```

OpenAPI permite ambas cosas, y a nivel de path es lo correcto: el parámetro
pertenece a la ruta, no al verbo. Cuando mañana haya un `PATCH /solicitudes/{id}`
lo hereda sin repetirlo.

### 5. Escribir el filtro de `GET /solicitudes`

El parámetro `estado` referencia el enum que ya existía, en lugar de repetir los
cuatro valores:

```yaml
FiltroEstado:
  name: estado
  in: query
  required: false
  schema:
    $ref: '#/components/schemas/Estado'
```

Así, el día que el enum crezca, el filtro crece solo. Y el `400` por estado
inválido queda **derivado del esquema**, no inventado en la ruta.

Aquí está la distinción que más se equivoca al implementar:

| Caso | Respuesta |
| --- | --- |
| `?estado=enviada` y hay tres | `200` con tres elementos |
| `?estado=enviada` y no hay ninguna | `200` con `[]` — **no** `404` |
| `?estado=pendiente` (no está en el enum) | `400` con `Error` |
| sin `?estado` | `200` con todas |

Las dos filas centrales son las que se confunden: *filtro válido sin resultados*
es un éxito; *filtro inválido* es un error del cliente.

### 6. Escribir `POST /solicitudes`

El `201` lleva cabecera `Location` con la ruta del recurso creado, que es la
convención HTTP para una creación y le ahorra al cliente componer la URL.

El `400` usa `examples` en plural, con tres casos nombrados:

```yaml
examples:
  tipoDesconocido:      # el tipo no está en el catálogo
  solicitanteNoValido:  # el solicitante viene vacío
  campoAusente:         # falta 'tipo'
```

Tres situaciones distintas bajo el **mismo código**. Es exactamente el síntoma de
que a `Error` le falta `codigo`: hoy el frontend solo puede distinguirlas leyendo
prosa castellana. Documentar los tres ejemplos deja el problema a la vista en vez
de esconderlo.

### 7. Escribir `POST /solicitudes/{id}/transiciones`

La operación con más superficie de error, y el motivo por el que el paso existe.
La regla que se escribió en la `description`:

```
borrador --enviar--> enviada --aprobar--> aprobada
                             --rechazar-> rechazada
```

Cualquier otra combinación de estado y acción es `409`. El orden en que el
servidor tiene que comprobar las cosas **es el orden de los códigos**:

| Orden | Comprobación | Si falla |
| --- | --- | --- |
| 1 | ¿El `id` de la ruta es un UUID? | `400` |
| 2 | ¿La `accion` está en el enum? | `400` |
| 3 | ¿Existe la solicitud? | `404` |
| 4 | ¿La transición es legal desde el estado actual? | `409` |

Invertir 3 y 4 filtra información: contestar `409` sobre una solicitud que no
existe le confirma a quien pregunta que el id es real. Y el `409` lleva dos
ejemplos —`estadoFinal` y `transicionNoPermitida`— porque "ya está aprobada" y
"todavía es borrador" son fallos distintos para el operador que los lee.

### 8. Verificar

Tres comprobaciones, de menos a más exigente. La tercera es la que
[CONTRATO.md](CONTRATO.md) dejaba encargada: *"merece la pena volver a pasar el
`lint` después de añadir las rutas"*.

## Cómo verificar

Desde la raíz, sin añadir nada al repo ni tocar el lockfile.

**1. Que el YAML parsea y las siete operaciones están donde se espera.**

```bash
npx --yes yaml@2 --single --json < packages/contrato/openapi.yaml | node -e "
  const d = JSON.parse(require('fs').readFileSync(0,'utf8'));
  for (const [ruta, item] of Object.entries(d.paths))
    for (const m of ['get','post','put','patch','delete'])
      if (item[m]) console.log(m.toUpperCase().padEnd(5), ruta.padEnd(31),
        item[m].operationId.padEnd(18), Object.keys(item[m].responses).join(','));
"
```

Salida obtenida:

```
GET   /salud                          obtenerSalud       200,500
GET   /tipos                          listarTipos        200,500
GET   /operadores                     listarOperadores   200,500
GET   /solicitudes                    listarSolicitudes  200,400,500
POST  /solicitudes                    crearSolicitud     201,400,500
GET   /solicitudes/{id}               obtenerSolicitud   200,400,404,500
POST  /solicitudes/{id}/transiciones  aplicarTransicion  200,400,404,409,500
```

**2. Que es OpenAPI 3.0.3 estructuralmente correcto y no hay `$ref` rotos.** Un
`$ref` que apunta a un componente inexistente es YAML perfectamente válido, así
que el paso 1 no lo detecta:

```bash
npx --yes @redocly/cli lint packages/contrato/openapi.yaml
```

**3. Que los `operationId` son únicos.** Importa porque de ahí salen los nombres
de función de cualquier cliente generado; dos iguales producen código que no
compila. El `lint` del paso 2 ya lo cubre con la regla `operation-operationId-unique`.

## Resultado del `lint`, y qué significa cada aviso

```
Validation failed with 7 errors and 4 warnings.
```

Comparado con el paso anterior (1 error, 7 warnings), lo relevante es **lo que
desapareció**: los seis `no-unused-components` ya no están. Cada esquema está
ahora referenciado desde alguna ruta, que era justo lo que
[CONTRATO.md](CONTRATO.md) predijo que se arreglaría solo.

| Aviso | Veces | Qué es | Qué hacer |
| --- | --- | --- | --- |
| `security-defined` | 7 (los **errores**) | Ninguna operación declara `security` | **No ignorar.** Ver abajo |
| `operation-4xx-response` | 3 | `/salud`, `/tipos` y `/operadores` no tienen ningún `4xx` | Ignorar: no aceptan entrada del cliente, así que no hay nada que pueda venir mal |
| `info-license` | 1 | Falta `info.license` | Ignorar o añadir la licencia del proyecto |

Los **siete errores son el mismo error, uno por operación**: el contrato describe
una API sin autenticación. El linter no sabe que esto es una bandeja de
back-office; se limita a exigir que cada operación diga si es pública o no. Que
las siete lo incumplan no es ruido, es la confirmación mecánica del hueco más
grande que queda abierto (ver la sección siguiente).

Se arregla en dos sitios —`components/securitySchemes` y un `security` global—
pero es una decisión de producto, no de formato: **qué** autentica (sesión, token,
SSO corporativo) y si un operador puede aprobar cualquier solicitud o solo las
suyas. Por eso se deja pendiente en vez de inventarlo.

## Decisiones tomadas que no estaban en el enunciado

El enunciado pedía siete operaciones con sus códigos. Estas cinco cosas no venían
dadas y se decidieron al escribir:

| Decisión | Qué se eligió | Por qué |
| --- | --- | --- |
| `500` en las siete | Declarado explícitamente | Se pidieron "todas las respuestas posibles"; un fallo inesperado lo es en cualquier operación |
| `400` por UUID mal formado | En las dos rutas con `{id}` | `GET /solicitudes/SOL-2026-0007` no es *"no existe"*, es *"eso no es un identificador"*. Resuelve además la pregunta que CONTRATO.md dejaba abierta: **en la URL va el `id`, no la `referencia`** |
| Cabecera `Location` | En el `201` de `crearSolicitud` | Convención HTTP para creación |
| Array desnudo en los listados | `[...]`, no `{ datos: [...], total: n }` | CONTRATO.md marcaba esta decisión como pendiente. Se elige lo simple **a sabiendas de que paginar después es un cambio incompatible** |
| `/transiciones` como sub-recurso | `POST .../transiciones`, no `PATCH /solicitudes/{id}` | Un `PATCH` del campo `estado` invita a creer que se puede escribir cualquier estado. Un sub-recurso deja claro que solo se piden **acciones**, y es donde encajará el histórico |

La cuarta es la más reversible en apariencia y la menos en la práctica: en cuanto
el frontend haga `respuesta.map(...)`, envolver la lista rompe a todos los
clientes. Merece una decisión consciente antes de generar tipos.

## Lo que el contrato todavía no dice

Huecos que siguen abiertos tras este paso, ordenados por lo que cuesta arreglarlos
más tarde.

**No hay autenticación ni autorización.** Es el hueco grande, y el que el `lint`
señala siete veces. Además de `401`, una bandeja de back-office casi seguro
necesita `403`: ¿puede cualquier operador aprobar cualquier solicitud? Añadirlo
después obliga a revisar las siete operaciones.

**Nada escribe el campo `operador`.** `Solicitud` lo lleva desde
[CONTRATO.md](CONTRATO.md), pero **ninguna de las siete rutas lo asigna ni lo
cambia**. El modelo de datos tiene un campo que la API no sabe rellenar. Falta una
operación de asignación — no es un código de error que falte, es una ruta.

**Concurrencia entre operadores.** Si dos abren la misma solicitud `enviada` y uno
aprueba y otro rechaza, el segundo recibe `409` **por casualidad** (porque el
estado ya es final), no porque el contrato modele la colisión. Sin `ETag`/`If-Match`
no hay `412`, y en las transiciones donde ambos serían legales el resultado
depende del orden de llegada.

**A `Error` le sigue faltando `codigo`.** Ya estaba apuntado en CONTRATO.md; este
paso lo vuelve urgente, porque ahora hay tres `400` distintos en `crearSolicitud`
y dos `409` distintos en `aplicarTransicion` que el frontend solo puede separar
leyendo castellano.

**Errores de protocolo sin declarar**, los tres deliberadamente delegados al
framework: `415` (cuerpo enviado sin `Content-Type: application/json`), `405` y
`406`. El JSON sintácticamente roto cae hoy en el `400` genérico, sin distinguirse
de "el tipo no existe".

**Comportamiento de `?estado` repetido o vacío.** `?estado=a&estado=b` y
`?estado=` no están definidos, y cada framework hace algo distinto. El enum implica
`400`, pero no está dicho.

**Sin paginación y sin idempotencia.** `GET /solicitudes` devuelve todo; cuando
haya `limit`/`offset` traerán sus propios `400`. Y dos `POST /solicitudes`
idénticos crean dos solicitudes: se asume correcto, porque nada es único por
`tipo` + `solicitante`, pero si no lo fuera faltaría un `409`.

## Siguiente paso

El contrato ya describe una API completa, pero `packages/contrato` sigue sin
`main` ni `exports`: `import '@tramitador/contrato'` continúa fallando. Generar
tipos TypeScript desde el YAML (`openapi-typescript` o similar) y exponerlos es lo
que convierte este documento en algo que el compilador puede hacer cumplir — y el
momento a partir del cual cada decisión de arriba cuesta una migración.
