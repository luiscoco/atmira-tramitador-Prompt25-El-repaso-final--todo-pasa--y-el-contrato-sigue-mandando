# La verificación final — comprobar la aplicación entera sin arreglar nada por el camino

`24. INTEGRACION.md` cerró con una línea que este paso convierte en trabajo:

> **El enlace del workspace sigue rompiéndose solo.** Cuatro pasos seguidos. Ya
> no merece la pena anotarlo otra vez: merece la pena averiguar qué lo borra.

El encargo de este paso no pide escribir código. Pide ejecutar:

> Antes de dar por terminada la aplicación, ejecuta en este orden y pégame el
> resultado de cada uno:
>
> 1. `npm run verifica:contrato`
> 2. `npm run lint` (en las tres piezas)
> 3. `npm test` (en las tres piezas)
> 4. `npm run build`
> 5. `npm run dev`, y un recorrido manual: cargar la bandeja, seleccionar una
>    "enviada", aprobarla, confirmar que cambia sin recargar la página.
>
> Si algo falla, dime exactamente qué comando falló y qué mensaje dio, sin
> intentar "arreglarlo silenciosamente" — quiero decidir yo cómo corregirlo.

La última frase es la que define el paso. **Un encargo de verificación con la
reparación explícitamente prohibida** es una cosa distinta de un encargo de
arreglo, y la diferencia no es de cortesía: si quien verifica repara sobre la
marcha, el informe final dice "todo verde" y nadie se entera de que había algo
roto. El valor de este paso estaba en el intervalo entre encontrar el fallo y
tocarlo.

Los cinco comandos se ejecutaron dos veces: una en modo informe —tres de los
cinco fallaron— y otra después de la autorización para reparar.

## Qué hay

```
(ningún fichero de la aplicación modificado)
25. VERIFICACION.md   NUEVO   <- este documento
```

**No se tocó una sola línea de código.** Ni de `apps/backend`, ni de
`apps/frontend`, ni de `packages/contrato`, ni de `data/`. Lo que estaba roto no
estaba en el código: estaba en `node_modules/`.

Eso merece decirse en voz alta porque los síntomas apuntaban a lo contrario. Los
doce errores del `build` señalaban ficheros `.tsx` con nombre y número de línea,
y ninguno de esos ficheros tenía nada mal.

## Los pasos que se siguieron

### 1. Leer los `package.json` antes de ejecutar nada

El enunciado da por supuestas dos cosas que no eran ciertas, y las dos se ven
leyendo los cuatro `package.json` antes de escribir el primer comando:

- **«`npm run lint` (en las tres piezas)»** — no hay un `lint` por pieza.
  Existe uno solo, en la raíz, que es `eslint .`. Lo mismo con `test`:
  `vitest run` desde la raíz. Los dos barren el monorepo entero de una pasada,
  así que la intención del enunciado se cumple, pero no hay tres comandos que
  ejecutar.

- **«`npm run build`»** — **no existe en la raíz.** Solo `apps/frontend` define
  uno. Y es deliberado: los `package.json` de `backend` y `contrato` explican
  por escrito que no compilan a `dist/` a propósito, porque `tsx` y Vite leen
  TypeScript directamente.

Avisar de esto antes de ejecutar, y no al llegar al error, es la diferencia
entre un informe y una sorpresa.

### 2. El paso 1 pasa, y eso es engañoso

```
> node scripts/verifica.mjs
✔ src/tipos.gen.ts coincide con lo que genera openapi.yaml.
```

Verde. Y sin embargo la aplicación estaba rota de arriba abajo.

Vale la pena entender por qué, porque es un ejemplo limpio de lo que un
comando verde no demuestra. `verifica:contrato` corre **dentro** de
`packages/contrato`, compara dos ficheros por ruta relativa y no importa
`@tramitador/contrato` en ningún momento. Nunca ejerce el enlace del workspace,
que era justo lo que estaba roto. El lint tampoco: ESLint no resuelve imports.

El orden del enunciado empieza, sin querer, por los dos únicos comandos ciegos
al fallo que venía.

### 3. Comprobar que el lint mira de verdad las tres piezas

`eslint .` terminó con salida vacía y código 0. Un éxito silencioso y un
conjunto vacío de ficheros se parecen demasiado, así que se contó:

```
Ficheros linteados: 27
{ backend: 12, frontend: 12, contrato: 2, raiz: 1 }
```

Ahora el verde significa algo. Las tres piezas están cubiertas.

### 4. El paso 3 rompe, y rompe en dos formas distintas

```
 Test Files  6 failed | 2 passed (8)
      Tests  3 failed | 60 passed (63)

Error: Cannot find package '@tramitador/contrato' imported from
  .../apps/backend/src/datos/repositorio.ts
```

Las seis suites caídas lo hacen de tres maneras que conviene separar, porque
cada una dice algo distinto:

- **Cinco suites no llegan a cargarse.** Node o Vite no resuelven
  `@tramitador/contrato` y el fichero ni se ejecuta. Sus tests no salen como
  fallidos: **no salen en absoluto**.
- **`servidor.test.ts` sí carga, y falla con otro mensaje.** Sus tres tests
  lanzan un subproceso de verdad, y el que muere con `ERR_MODULE_NOT_FOUND` es
  el hijo. El test lo informa como "el proceso terminó con código 1".
- **Sesenta tests pasan.** Son los que no importan el contrato.

De aquí sale el dato que más engaña de todo el paso, y que se explica en el
punto 9: **63 tests contados**, cuando `24. INTEGRACION.md` había dejado 180.

### 5. El paso 4 confirma el diagnóstico y añade dos errores falsos

```
src/api/cliente.ts(41,8): error TS2307: Cannot find module '@tramitador/contrato'
src/App.tsx(12,56): error TS2307: ...
src/componentes/Bandeja.tsx(18,38): error TS2307: ...
...
src/componentes/EstadoChip.tsx(71,11): error TS2339: Property 'texto' does not exist
src/dominio/acciones.ts(126,27): error TS7006: Parameter 'accion' implicitly has an 'any'
```

Doce errores, pero **no doce problemas**. Diez son el mismo `TS2307` repetido.
Los otros dos —el `TS2339` de `EstadoChip` y el `TS7006` de `acciones`— son
consecuencia: cuando el tipo importado no se resuelve, `ETIQUETAS[estado]` pasa
a ser `… | undefined` y el parámetro de un `map` se queda sin inferir.

En el informe se marcaron como probablemente derivados, **sin darlo por hecho**.
Después del arreglo desaparecieron solos, lo que lo confirmó. La distinción
importa porque un informe que dice "doce errores de tipos" invita a abrir doce
ficheros.

### 6. El paso 5 no llega a arrancar

```
> tsx watch src/servidor.ts
Error: Cannot find package '.../node_modules/@tramitador/contrato/index.js'
       imported from .../apps/backend/src/datos/repositorio.ts
```

Sin backend no hay bandeja que cargar, así que **el recorrido manual no se hizo
en la primera pasada**. Se dijo así de claro en el informe, en vez de dar por
bueno lo que los tests de `App.test.tsx` ya cubren: un test de integración con
el `fetch` mockeado y un recorrido con el backend real no prueban lo mismo.

Un detalle de ese mensaje que despista: Node dice buscar
`@tramitador/contrato/index.js`, pero el `package.json` del contrato apunta a
`./src/index.ts`. No es que `main` esté mal. Es que Node, al encontrar un
directorio vacío, cae al *legacy main resolve* y se inventa el `index.js`.

### 7. El diagnóstico: carpetas vacías donde debía haber junctions

Los cuatro mensajes distintos venían del mismo sitio:

```
node_modules/@tramitador/backend    -> directorio vacío
node_modules/@tramitador/contrato   -> directorio vacío
node_modules/@tramitador/frontend   -> directorio vacío
```

Y en Windows la confirmación está en los atributos:

```
LinkType   :                        <- vacío
Attributes : Directory              <- sin ReparsePoint
```

Un junction de npm aparece como `LinkType : Junction` y
`Attributes : Directory, ReparsePoint`. Estos eran **carpetas de verdad, y
vacías**. El fuente seguía intacto en `packages/contrato/src/`.

Esto matiza cómo lo venían anotando los documentos 21 a 24 —"el enlace se rompe
solo"—: el enlace no se borra, se **sustituye por un directorio vacío**. Es una
distinción con consecuencias prácticas, porque un enlace ausente y un directorio
vacío se comportan distinto: si `node_modules/@tramitador/contrato` no existiera,
Node seguiría subiendo por el árbol buscando el paquete. Al existir y estar
vacío, la búsqueda **termina ahí**, en un sitio sin `package.json`.

### 8. El arreglo: `npm install`, y nada más

Con la reparación ya autorizada, lo primero que se probó fue lo menos
destructivo:

```
changed 3 packages, and audited 285 packages in 2s
```

Esos tres paquetes eran los tres enlaces. Quedó así:

```
contrato : Junction -> ...\packages\contrato
backend  : Junction -> ...\apps\backend
frontend : Junction -> ...\apps\frontend
```

**No se borró `node_modules/`, ni se tocó `package-lock.json`.** El `rm -rf
node_modules && npm install` es el reflejo habitual ante esto y aquí habría
sobrado: cinco minutos de descarga para arreglar tres enlaces, y un lockfile
reescrito sin necesidad.

### 9. La suite pasa de 63 a 180, y no es que se hayan añadido tests

```
 Test Files  8 passed (8)
      Tests  180 passed (180)
```

Leído junto al `63` de antes, parece que aparecieron 117 tests. No apareció
ninguno: **117 tests no llegaban a contarse** porque las cinco suites que los
contienen no cargaban. Un contador de tests solo cuenta lo que se ha podido
registrar, y una suite que revienta al importar no registra nada.

De ahí que `24. INTEGRACION.md` insista en medir la línea de partida antes de
tocar nada. El `180` de hoy coincide exactamente con el `180` que aquel
documento dejó anotado, y esa coincidencia es la prueba de que el arreglo no
cambió el comportamiento de nada: solo dejó que se ejecutara lo que ya existía.

### 10. Los puertos estaban ocupados, y por otro proyecto

Al arrancar `npm run dev` para el recorrido:

```
Error: listen EADDRINUSE: address already in use 127.0.0.1:3001
Error: Port 5173 is already in use
```

Aquí estuvo el momento más peligroso del paso. Un `curl` al 3001 respondía
`HTTP 200` con doce solicitudes de aspecto perfectamente razonable. **Y no eran
de este proyecto:**

```
PID 34616 (puerto 3001) -> .../Prompt16/node_modules/tsx/... src/servidor.ts
PID 31724 (puerto 5173) -> .../Prompt17/node_modules/.bin/../vite/bin/vite.js
```

Estamos en `Prompt25`. Un recorrido hecho contra esos puertos habría salido
verde entero **sin haber probado ni una línea de este código**, y el informe
habría sido falso sin que nada chirriara. Los datos de prueba son los mismos en
todos los `Prompt<N>`, así que ni siquiera el contenido delataba el cambiazo.

La comprobación que lo destapó —mirar la línea de comandos del proceso que
ocupa el puerto, no solo si responde— es la que conviene recordar cuando se
trabaja con una carpeta por paso y servidores que se quedan abiertos de días
anteriores.

### 11. Arrancar en puertos libres sin tocar el repo ni matar nada ajeno

Dos salidas, y por qué se eligió la segunda:

- **Matar los procesos de `Prompt16` y `Prompt17`.** Rápido, pero son procesos
  de otro trabajo, y cerrarlos no es decisión de quien está verificando este.

- **Levantar `Prompt25` en 3025 y 5225.** El backend lo permite de fábrica:
  `servidor.ts` lee `process.env.PORT`. El frontend no, y ahí estaba la
  dificultad: `vite.config.ts` tiene `strictPort: true`, el 5173 escrito a mano
  y el proxy clavado en `http://127.0.0.1:3001`.

Se resolvió con un config temporal que **extiende el real** en vez de copiarlo:

```js
import base from './vite.config';
export default {
  ...base,
  server: { ...base.server, port: 5225, strictPort: true,
            proxy: { '/api': { target: 'http://127.0.0.1:3025', ... } } },
};
```

Extenderlo y no duplicarlo importa: lo que se probó siguió siendo la
configuración real —el plugin de React, todo lo demás— con dos números
cambiados. El fichero se borró al terminar.

Un intento anterior, con el config en un directorio temporal fuera del
proyecto, **no funcionó**: rolldown no resuelve rutas absolutas de Windows con
espacios y paréntesis, y la del curso tiene las dos cosas.

### 13. El recorrido, en un Chrome de verdad

No hay Playwright ni Puppeteer instalados, y no hacía falta instalarlos: hay

Los selectores no se adivinaron; salen de leer los componentes. `Bandeja.tsx`
pinta la referencia como `<th scope="row"><button>` —un botón de verdad, no un

> contrato y no.

El recorrido completo:

```

[3] Clic en SOL-2026-0003 (enviada) -> el detalle ofrece ["Aprobar","Rechazar"]
```

### 14. Cómo se comprobó el "sin recargar la página"

Es la parte del enunciado que se presta a darse por buena de un vistazo, porque
una recarga rápida en local se ve casi igual. Así que no se miró: se midió, de
tres formas independientes.

**Un testigo en `window`.** Antes de aprobar:

```js
window.__testigo = 'vivo-' + Date.now();
```

Una recarga se lleva por delante el contexto de JavaScript y esa variable con
él. Siguió valiendo `vivo-1789811988559` después del cambio de estado.

**El contador de navegaciones.** `performance.getEntriesByType('navigation')`
devolvió `1` al final: solo la carga inicial.

**El log del backend.** Con `LOG=1`, en orden cronológico:

```
    +0 ms  GET  /api/solicitudes          <- un curl de comprobación, antes de abrir nada
+77049 ms  GET  /api/solicitudes  tipos  operadores   <- carga inicial
+77050 ms  GET  /api/solicitudes  tipos  operadores   <- otra vez (StrictMode)
+77126 ms  POST /api/solicitudes/5e8c.../transiciones <- "Aprobar"
+77299 ms  GET  /api/solicitudes          <- la comprobación del paso [7]
```

Lo que interesa es lo que **no** hay entre el `POST` y el final: la aplicación no
volvió a pedir `tipos` ni `operadores`. Si la pantalla se hubiera repintado
recargando —que es la otra forma de "cambiar sin recargar" que habría pasado los
dos controles anteriores—, se vería una tercera tanda de las tres listas, porque
`recargar` las pide todas. No la hay. El único `GET` posterior es el que lanzó
el propio script de verificación.

La doble carga inicial de `+77049`/`+77050` no es un fallo: es
`<React.StrictMode>` montando dos veces en desarrollo, que es lo que hace a
propósito para destapar efectos sin limpiar.

Las tres señales juntas dicen lo mismo desde tres sitios: hubo una petición, y el
estado de React se actualizó con su respuesta.

## Cómo verificar

### 1. El enlace del workspace, primero

```powershell
Get-Item node_modules\@tramitador\* | Select-Object Name, LinkType
# Los tres deben decir: Junction
```

Si dicen `Directory` a secas, es esto otra vez. `npm install` y a seguir.

### 2. Los cuatro comandos

```bash
npm run verifica:contrato   # -> tipos.gen.ts coincide con openapi.yaml
npm run lint                # -> vacío
npm test                    # -> Test Files 8 passed (8) / Tests 180 passed (180)
npm run build -w @tramitador/frontend   # -> built in ~130ms
```

El `-w` del último no es opcional: en la raíz no hay `build`.

### 3. El recorrido, a mano

Dos terminales —`npm run dev` y `npm run dev:frontend`, que el `package.json` de
la raíz explica por qué no son uno solo—, y en el navegador: cargar, clic en una
"enviada", "Aprobar", y mirar que la fila cambia. Para lo de "sin recargar", la
pestaña Network con "Preserve log": debe aparecer un `POST` a `/transiciones` y
ningún documento nuevo.

Y si algo no responde en `127.0.0.1`, probar `localhost`: **Vite escucha solo en
IPv6** (`::1`). Con el navegador da igual, pero con `curl` parece que el
servidor no está arrancado cuando sí lo está.

## Lo que todavía no está

**Solo se recorrió el camino feliz, otra vez.** Igual que en
`24. INTEGRACION.md`, pero ahora contra el backend real, donde además se podría
provocar de verdad el 409 de una transición ilegal. Nadie ha visto con sus ojos
cómo se lee ese error en pantalla.

**No se probó `npm run preview`.** El `build` genera `dist/`, y nadie ha abierto
ese `dist/`. El propio `package.json` del frontend avisa de que ahí **no hay
proxy**: lo que sirva `dist/` en producción tendrá que resolver `/api` por su

Dos hipótesis que nadie ha comprobado: que los `Prompt<N>` se creen copiando el
anterior con una herramienta que no preserva reparse points y deja la carpeta

siempre y mirar los atributos antes de tocar nada.

raíz desde hace varios pasos, con la solución escrita (`concurrently` o
`npm-run-all`) y sin añadir.

en un directorio temporal y se ha ido con él. Convertirlo en algo reproducible

haber comprobado esto una vez y poder comprobarlo en cada cambio.
