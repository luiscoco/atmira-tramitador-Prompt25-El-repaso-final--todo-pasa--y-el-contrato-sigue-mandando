# El frontend — un origen, y por eso ni CORS ni variables de entorno

`16. ARRANQUE.md` cerró su sección "Lo que todavía no está" con una frase de una
línea:

> **El frontend no se levanta.** Es lo que dice el `"//"` de la raíz, y es el
> siguiente paso.

Este es ese paso. Hasta ahora `apps/frontend/` eran dos ficheros escritos en
`2. TYPESCRIPT.md` —un `package.json` con una sola dependencia y un
`tsconfig.json` con `jsx: "react-jsx"`— apuntando a una aplicación que no
existía. Aquí aparece la aplicación, y con ella la decisión que ordena todo lo
demás: **el navegador solo va a ver un origen**.

```
apps/frontend/package.json      react, react-dom, vite, @vitejs/plugin-react, + scripts
apps/frontend/vite.config.ts    NUEVO  <- el puerto y el proxy
apps/frontend/index.html        NUEVO
apps/frontend/src/main.tsx      NUEVO
apps/frontend/src/App.tsx       NUEVO
apps/frontend/src/vite-env.d.ts NUEVO
apps/frontend/tsconfig.json     + vite.config.ts en `include`
package.json (raíz)             + scripts.dev:frontend
```

No se ha tocado ni una línea del backend.

## Qué hay

| Fichero | Qué hace |
| --- | --- |
| `vite.config.ts` | `port: 5173`, `strictPort: true` y proxy de `/api` al `127.0.0.1:3001` |
| `index.html` | El punto de entrada real del grafo de módulos. En la raíz del workspace, no en `public/` |
| `src/main.tsx` | Coge el `<div id="root">` y monta React. El `servidor.ts` del frontend |
| `src/App.tsx` | `fetch('/api/solicitudes')` con los tipos de `@tramitador/contrato` |
| `src/vite-env.d.ts` | Los tipos ambientales de Vite (`import.meta.env`, imports que no son JS) |

| Script | Dónde | Qué hace |
| --- | --- | --- |
| `dev` | `apps/frontend` | `vite` — el servidor de desarrollo con HMR y proxy |
| `build` | `apps/frontend` | `tsc --noEmit && vite build` |
| `preview` | `apps/frontend` | Sirve `dist/` tal cual: sin proxy y sin recarga |
| `comprobar` | `apps/frontend` | Solo el type-check, mismo nombre que en `@tramitador/contrato` |
| `dev:frontend` | raíz | `npm run dev --workspace @tramitador/frontend` |

La misma regla que ordena los scripts del backend en `16. ARRANQUE.md`: **el
script que sabe cómo se ejecuta el frontend vive en el frontend**. La raíz no
menciona `vite`, ni `index.html`, ni el 5173.

## Los pasos que se siguieron

### 1. Rellenar el workspace, no crearlo con `npm create vite`

La tentación era `npm create vite@latest frontend -- --template react-ts` y
dejar que la plantilla lo montara todo. No se hizo, y por un motivo concreto:
esa plantilla trae **su propio `tsconfig`**, partido en `tsconfig.app.json` y
`tsconfig.node.json` con un `tsconfig.json` de referencias por encima, y
pisaría el que `2. TYPESCRIPT.md` escribió a mano extendiendo
`tsconfig.base.json`.

Ese fichero no es decorativo: es el que hereda `strict`,
`noUncheckedIndexedAccess`, `verbatimModuleSyntax` y el resto de las reglas que
el monorepo decidió una vez para los tres workspaces. Cambiarlo por el de la
plantilla habría dejado el frontend con reglas distintas a las del backend sin
que nadie lo decidiera.

Lo que había ya, y se conservó entero:

```
apps/frontend/package.json   name, private, type: module, @tramitador/contrato
apps/frontend/tsconfig.json  lib DOM+DOM.Iterable, jsx: react-jsx, noEmit
```

El `"jsx": "react-jsx"` de ese tsconfig es además lo que explica que ningún
`.tsx` de este paso escriba `import React`: el runtime automático lo inyecta el
compilador.

### 2. El proxy, que es todo el enunciado

Sin proxy hay **dos orígenes**. La aplicación se descarga de
`http://localhost:5173` y la API vive en `http://127.0.0.1:3001`; para el
navegador eso son sitios distintos —basta con que difiera el puerto— y la
consecuencia es doble:

- El cliente tiene que escribir la URL absoluta del backend. De ahí salen las
  `VITE_API_URL` que hay que definir, documentar y cambiar en cada entorno.
- El backend tiene que dar permiso con cabeceras CORS, preflight `OPTIONS`
  incluido.

Con el proxy solo hay **un** origen. `fetch('/api/solicitudes')` resuelve contra
la página actual —o sea `http://localhost:5173/api/solicitudes`— y esa petición
la atiende el servidor de Vite, que la reenvía al 3001. Lo que ocurre en ese
segundo tramo es una petición HTTP de servidor a servidor, hecha por Node, fuera
del navegador.

Ahí está la frase entera:

> La política del mismo origen es una regla **del navegador**, no del protocolo.
> Donde no hay navegador, no hay nada que autorizar.

De donde salen los dos efectos que se buscaban:

- **Sin CORS**, porque el navegador nunca llega a ver una petición a otro origen.
- **Sin variables de entorno**, porque una ruta relativa vale igual en
  desarrollo (donde la atiende este proxy) que en producción (donde la atiende
  el servidor que sirva `dist/` bajo el mismo dominio). No hay nada que
  configurar porque no hay ningún host escrito en el código del cliente.

Las cabeceras CORS de `app.ts` **no se han quitado**. Siguen puestas y siguen
sirviendo para quien llame al 3001 directamente —un `curl`, un test, otro
cliente—; lo que ha cambiado es que el frontend ya no depende de ellas.

### 3. `'/api'` es un prefijo, y no se reescribe

Las dos cosas que más se equivocan en un `server.proxy`, las dos en la misma
clave:

```ts
proxy: {
  '/api': {
    target: BACKEND,
    // sin rewrite
  },
},
```

**Es un prefijo, no una ruta exacta.** Con esa sola entrada quedan cubiertas las
siete operaciones del contrato (`/api/salud`, `/api/tipos`, `/api/operadores`,
las cuatro de `/api/solicitudes`) sin listarlas.

**No lleva `rewrite`.** El reflejo aprendido es quitar el prefijo antes de
reenviar, y aquí eso rompería todo: el backend registra sus rutas con `/api`
dentro (`app.get('/api/salud', ...)`, porque `openapi.yaml` declara
`servers: [{ url: /api }]`). `app.ts` lo deja escrito en un comentario —"el
contrato dice `/api`, y una API que responde en dos sitios tiene dos
contratos"—. Un `rewrite` que borrara el prefijo convertiría las siete
operaciones en `404`.

### 4. `127.0.0.1` en el `target`, no `localhost`

Es la misma decisión que `servidor.ts` tomó para el `listen()`, y por el mismo
motivo escrito allí: `localhost` puede resolver a `::1` (IPv6) o a `127.0.0.1`
según la máquina, y el backend escucha **solo** en la IPv4.

La diferencia es dónde aparece el síntoma. Un proxy apuntado a
`http://localhost:3001` funciona hasta que el sistema decide resolver por IPv6,
y entonces da `ECONNREFUSED` con el backend perfectamente arrancado: el clásico
"el servidor está levantado pero el proxy no conecta". Las dos direcciones se
escriben iguales en los dos ficheros para que no haya un tercer sitio donde
puedan divergir.

### 5. `strictPort: true`: fallar antes que arrancar a medias

Por defecto, si el 5173 está ocupado, Vite busca el siguiente libre y lo anuncia
en la terminal. Es cómodo, y aquí sería el peor de los fallos posibles.

`apps/backend/src/app.ts` lista exactamente dos orígenes:

```ts
const ORIGENES_DE_DESARROLLO = ['http://localhost:5173', 'http://127.0.0.1:5173'] as const;
```

Un frontend en el 5174 arranca, carga, pinta... y muere en la primera llamada,
con un error de CORS en la consola del navegador y ninguna pista de que el
problema sea un número de puerto. Con `strictPort`, el arranque no ocurre y dice
por qué.

El número queda escrito en dos sitios (esa constante y el `PUERTO` de
`vite.config.ts`), y eso es una dependencia real: **cambiar uno sin el otro
rompe una de las dos formas de llamar a la API**. Está anotado en el comentario
de la constante, que es lo único que se puede hacer mientras un `.ts` del
backend y un `.ts` del frontend no compartan un módulo de configuración que
ninguno de los dos necesita.

### 6. `index.html` en la raíz del workspace

No es un detalle de colocación: en Vite el grafo de módulos **arranca en el
HTML**, no en un fichero de configuración. Vite sirve `index.html`, lee su
`<script type="module" src="/src/main.tsx">`, y desde ahí resuelve imports,
transforma TypeScript y JSX y engancha la recarga en caliente. En `vite build`
ese mismo HTML es la entrada del bundle.

Por eso va en la raíz del proyecto y no en `public/`: lo que hay en `public/` se
copia tal cual, sin pasar por el grafo, y un `index.html` ahí no se procesaría.

### 7. Añadir `vite.config.ts` al `include` del tsconfig

El `tsconfig.json` que había decía `"include": ["src"]`. `vite.config.ts` no
está bajo `src/` y no forma parte de la aplicación, así que con esa lista
**nadie lo comprobaba**: un `port: "5173"` con comillas o una opción de proxy
mal escrita solo se descubrirían al arrancar.

```json
"include": ["src", "vite.config.ts"]
```

Lo lee Vite, que lo transpila por su cuenta con esbuild; esta entrada solo añade
el type-check. La alternativa habitual —un `tsconfig.node.json` aparte, que es
lo que genera la plantilla oficial— existe para separar el `lib` de Node del
`lib` del navegador; aquí no hace falta, porque `vite.config.ts` no usa ninguna
API de Node (no hay `path.resolve`, no hay `process.env`) y pasa el check con el
`lib` de DOM que ya estaba.

### 8. `tsc --noEmit` delante de `vite build`

```json
"build": "tsc --noEmit && vite build"
```

La primera mitad no es redundante. Vite transpila con esbuild, y **esbuild borra
los tipos sin comprobarlos**: un `vite build` a secas produce un bundle correcto
a partir de código que no compila. Sin ese `tsc`, un error de tipos no rompe el
build, solo la aplicación en runtime.

Es la misma división que ya usa el monorepo en otro sitio: `tsc --noEmit` para
comprobar, el bundler para generar. El `noEmit` del tsconfig es lo que garantiza
que la primera mitad no escriba ni un `.js`.

### 9. El obstáculo: `EADDRINUSE` otra vez

Al arrancar el backend para probar el proxy:

```
No se pudo arrancar el servidor: Error: listen EADDRINUSE: address already in use 127.0.0.1:3001
```

El mismo mensaje que el paso 6 de `16. ARRANQUE.md`, y por la misma razón
genérica: hay procesos de desarrollo que sobreviven a la sesión que los lanzó.

La diferencia con aquella vez es el diagnóstico. Allí el proceso huérfano servía
**código viejo** —contestaba `/api/salud` y daba `404` en `/api/solicitudes`,
porque era anterior a las rutas de `14. SOLICITUDES.md`— y había que cerrarlo.
Aquí el proceso que ya estaba en el 3001 respondía correctamente a las dos, así
que servía el código actual y la verificación del proxy se hizo contra él.

La comprobación que separa un caso del otro es de una línea, y es la que hay que
hacer antes de cerrar nada: preguntarle al servidor qué sabe servir.

### 10. `dev:frontend` en la raíz, y por qué `dev` sigue arrancando uno solo

El `"//"` de `16. ARRANQUE.md` dejaba dicho qué tocaba hacer aquí:

> Cuando lo tenga, este script pasa a arrancar los dos a la vez (concurrently o
> npm-run-all) y `dev:backend` / `dev:frontend` siguen sirviendo para levantar
> uno solo.

Se ha hecho la mitad. `dev:frontend` existe; `dev` sigue delegando en
`dev:backend`. El motivo es que la otra mitad **no es un cambio de scripts, es
una dependencia nueva**, y esa decisión no se toma de paso:

```
npm run dev --workspaces   ->  los ejecuta en SERIE
```

Y el `tsx watch` del backend no termina nunca, así que el frontend no llegaría a
arrancar jamás. No hay forma de hacerlo con npm a secas: hace falta
`concurrently`, `npm-run-all` o equivalente. Mientras tanto, dos terminales, y
el `"//"` de la raíz reescrito para que diga eso mismo en el fichero y no solo
aquí.

### 3. La misma ruta por los dos caminos

Esta es la verificación del enunciado, y son dos `curl` idénticos salvo el

## Decisiones tomadas que no estaban en el enunciado

**`strictPort: true`.** El enunciado pedía "que escuche en el 5173". Sin esta
opción, Vite escucha en el 5173 *o en el siguiente que encuentre*, que no es lo
mismo cuando hay una lista de orígenes CORS al otro lado (paso 5).

**`changeOrigin: true`.** Reescribe la cabecera `Host` de la petición reenviada.
Hoy da igual: Fastify no enruta por `Host`, no hay virtual hosts. Se deja puesto
porque es lo que espera cualquier backend que sí la mire, y porque el día que el
`target` deje de ser loopback es lo que evita un rechazo por un `Host` que el
otro extremo no reconoce.

**`ws: false`.** El backend no tiene ningún WebSocket y el servidor de Vite sí
usa uno propio para el HMR. Dejar el reenvío de upgrades encendido en una ruta
que no lo necesita solo abre la puerta a que uno acabe en el sitio equivocado.

**`App.tsx` llama a la API en vez de pintar un "Hola mundo".** No es la interfaz
del tramitador —eso no es este paso—, es la comprobación de extremo a extremo de
que la tubería entera está montada: React pinta, el `fetch` relativo sale por el
proxy, el backend contesta y los tipos que llegan son los de
`@tramitador/contrato`. Un `<h1>` estático habría dejado el proxy sin probar
desde el navegador.

**`AbortController` en el `useEffect`.** `StrictMode` monta, desmonta y vuelve a
montar cada componente en desarrollo, así que el efecto corre dos veces. No es
un fallo: es el detector. Sin la limpieza, el doble montaje deja una respuesta
huérfana intentando escribir en un componente que ya no existe, y eso es
exactamente lo que `StrictMode` está ahí para enseñar.

**Ningún fichero CSS.** No se ha tomado ninguna decisión de diseño. La página es
fea a propósito: lo que este paso tiene que demostrar es la fontanería.

## Lo que todavía no está

**`npm run dev` sigue levantando solo el backend.** Falta la dependencia que
permita lanzar dos procesos en paralelo (paso 10). Es lo único del `"//"` de la
raíz que queda pendiente.

**El `as Solicitud[]` de `App.tsx` no valida nada.** `respuesta.json()` devuelve
`any`, y la aserción le dice al compilador lo que el contrato promete, no lo que
ha llegado de verdad. Es la costura donde los tipos dejan de comprobarse solos:
un backend que devolviera otra cosa pasaría sin ruido hasta el primer `.map`.
Cerrarla es meter un validador en runtime (zod, valibot) y decidir qué hacer
cuando la API incumple su propio contrato — que es una decisión de diseño, no un
`npm install`.

**No hay tests del frontend.** `vitest` está en la raíz y barre el árbol entero,
pero probar componentes necesita un entorno DOM (`jsdom` o `happy-dom`) y una
librería de render, y ninguna de las dos está. Los 163 tests que pasan hoy
(`npm test`, 6 ficheros) son todos del backend y del contrato; este paso no ha
añadido ninguno.

**El estado vive en un `useState` del componente raíz.** Sirve para una pantalla
y para una llamada. En cuanto haya filtros, creación y transiciones —las otras
seis operaciones del contrato— hará falta decidir dónde vive el estado del
servidor y cómo se invalida tras un `POST`.

**`operador` sigue sin escribirse desde ningún sitio.** El hueco que
`16. ARRANQUE.md` dejaba anotado no se cierra aquí, y ahora se nota más: hay un
`GET /api/operadores` que el frontend puede pedir y ninguna operación que
permita asignar uno. La decisión sigue estando en `openapi.yaml`, no en este
workspace.
