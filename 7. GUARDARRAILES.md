# Guardarraíles en `tramitador` — que el contrato y los tipos no se separen

`6. TIPOS.md` cerró con un agujero declarado en voz alta:

> **`npm run gen` no está enganchado a nada.** Es manual. Si alguien edita
> `openapi.yaml` y no lo ejecuta, `tipos.gen.ts` queda desfasado sin que nadie avise.

Este paso lo cierra. No añade funcionalidad: añade dos formas de que el proyecto
**deje de pasar** cuando el contrato y los tipos generados dicen cosas distintas.

La desincronización tiene dos caras, y hacen falta dos mecanismos porque ninguno
ve las dos:

- El YAML cambia y **nadie regenera**. La unión de TypeScript sigue siendo la
  vieja, así que el compilador no tiene de qué quejarse: para él todo encaja.
- Se regenera, pero las **constantes de runtime** (`ESTADOS`, `ACCIONES`) se
  quedan atrás. Aquí el YAML y el `.gen.ts` sí coinciden; lo que baila es el
  código escrito a mano.

## Qué hay

```
packages/contrato/src/index.ts          -> +55 líneas al final: 2 afirmaciones y el porqué
packages/contrato/scripts/verifica.mjs  -> NUEVO. 195 líneas. Regenera y compara bytes
packages/contrato/package.json          -> "comprobar" ahora encadena; +1 "verifica:contrato"
package.json (raíz)                     -> +1 script: delega en el workspace
```

Los dos guardarraíles no se solapan, **se encadenan**:

| | Guardarraíl 1 (afirmaciones de tipo) | Guardarraíl 2 (`verifica.mjs`) |
| --- | --- | --- |
| Qué compara | unión generada ↔ constante escrita a mano | `openapi.yaml` ↔ `src/tipos.gen.ts` |
| ¿Ve el YAML? | **No** | **Sí** |
| Cuándo salta | después de regenerar | en cuanto el YAML cambia |
| Lo ejecuta | `npm run comprobar` (y el editor, en vivo) | `npm run comprobar` y `npm run verifica:contrato` |

`comprobar` **no es `tsc` a secas**: lanza primero el guardarraíl 2 y solo si pasa
llama al compilador.

```json
"comprobar": "node scripts/verifica.mjs && tsc --noEmit"
```

Esa línea es la que hace que se cumpla lo que uno espera al leer esto por encima:
*toco solo el YAML y el proyecto deja de compilar*. Sin ella, tocar solo el YAML
deja `tsc` en verde, porque **el compilador nunca lee `openapi.yaml`** — sus
tipos vienen de `tipos.gen.ts`, que en ese momento todavía dice lo de antes.

Conviene tener clara la letra pequeña: lo que falla ahí no es el *type checker*,
es el script que corre justo antes. Un error del compilador contra un YAML que
nadie ha regenerado es imposible por construcción, y el precio de esa
imposibilidad se paga en un sitio concreto: **el editor no lo pinta en rojo**.
Las líneas onduladas de VS Code salen de `tsc`, y `tsc` sigue sin ver el YAML.
Hasta que alguien ejecute `npm run comprobar` (o CI lo haga por él), editar solo
el YAML se ve limpio en el editor.

## Los pasos que se siguieron

### 1. Comprobar la línea base antes de tocar nada

Todo el guardarraíl 2 descansa sobre una suposición que había que verificar
primero: que regenerar dos veces produce **exactamente los mismos bytes**. Si
`openapi-typescript` metiera una fecha, un hash o un orden no determinista en la
salida, la comparación byte a byte daría falsos positivos para siempre y el
script sería inútil.

```bash
cd packages/contrato
../../node_modules/.bin/openapi-typescript openapi.yaml -o /tmp/base.gen.ts
cmp /tmp/base.gen.ts src/tipos.gen.ts && echo IDENTICO
```

```
✨ openapi-typescript 7.13.0
🚀 openapi.yaml → /tmp/base.gen.ts [87.1ms]
IDENTICO
```

De paso se comprobó el otro detalle que puede arruinar una comparación de bytes
en Windows: el fichero committeado tiene finales de línea **LF**, no CRLF.

### 2. Escribir las afirmaciones de tipo en `index.ts`

`listaCompleta` (paso 6) ya obligaba a que los arrays no se quedaran cortos, pero
lo hacía de refilón, en la firma de una función, y su mensaje de error no dice
**qué** valor falta:

```
error TS2345: Argument of type 'string[]' is not assignable to parameter of type 'never'.
```

Lo nuevo repite la comprobación de forma explícita, en las dos direcciones, y
mete el valor descolgado **dentro del mensaje de error**:

```ts
/** Aparece en el error cuando la constante se ha quedado corta. */
interface FaltanEnLaConstante<_V extends string> {
  readonly _: unique symbol;
}

/** Aparece en el error cuando la constante tiene valores que ya no existen. */
interface SobranEnLaConstante<_V extends string> {
  readonly _: unique symbol;
}

type MismosValores<U extends string, L extends readonly string[]> = [
  Exclude<U, L[number]>,
] extends [never]
  ? [Exclude<L[number], U>] extends [never]
    ? true
    : SobranEnLaConstante<Exclude<L[number], U>>
  : FaltanEnLaConstante<Exclude<U, L[number]>>;

/** Rompe la compilación si `C` no es exactamente `true`. */
type Afirma<C extends true> = C;

export type ESTADOS_CUBRE_ESTADO = Afirma<MismosValores<Estado, typeof ESTADOS>>;
export type ACCIONES_CUBRE_ACCION = Afirma<MismosValores<Accion, typeof ACCIONES>>;
```

Las dos direcciones que comprueba `MismosValores`, sobre `Estado`:

- **unión → constante**: todo valor del enum del YAML está en `ESTADOS`. Falla
  cuando alguien añade un estado al contrato, regenera y se olvida del array.
- **constante → unión**: todo valor de `ESTADOS` sigue existiendo en el enum.
  Falla cuando alguien borra o renombra un estado y la constante se queda con un
  valor fantasma.

Los corchetes de `[Exclude<...>] extends [never]` no son decorativos: sin ellos
el condicional es **distributivo** y una unión vacía cortocircuitaría la
comparación, dando `true` por la vía equivocada. Envolver los dos lados en una
tupla desactiva esa distribución.

El truco que hace legible el error está en `Afirma<C extends true>`: cuando `C`
no es `true`, TypeScript imprime el tipo que sí es, y ese tipo lleva el literal
dentro.

#### Por qué van `export`ados

No es decorativo y tampoco es que formen parte de la API que alguien vaya a usar.
`tsconfig.base.json` tiene `noUnusedLocals: true`, y un alias de tipo no
exportado y no usado en ninguna parte es exactamente eso: un local sin usar. TS
lo tumbaría antes de llegar a evaluar la afirmación.

El prefijo `_` no salva aquí: `argsIgnorePattern` / `varsIgnorePattern` son
convenciones de ESLint, y `noUnusedParameters` exime a los parámetros, pero
`noUnusedLocals` no exime a los locales por llevar guion bajo.

Exportarlos los hace parte del paquete, sí, pero son tipos sin habitantes útiles:
nadie va a escribir `ESTADOS_CUBRE_ESTADO` en una firma.

### 3. Escribir `scripts/verifica.mjs`

La lógica cabe en un párrafo: regenerar en un directorio temporal, leer los dos
ficheros como `Buffer` y comparar con `.equals()`. No interpreta nada — si un
byte baila, falla.

Lo que ocupa el resto del fichero es el mensaje de error. Decir "no coinciden" y
callarse obliga a quien lo lee a ir a buscar el qué, así que el script localiza
la primera línea distinta y la enfrenta con la del repo.

Dos cosas que **solo se descubren ejecutándolo**, y que están resueltas en el
código:

**El CLI no se resuelve por su subpath.** Lo natural sería
`require.resolve('openapi-typescript/bin/cli.js')`. No funciona:

```
Error: Cannot find module '...\node_modules\openapi-typescript\bin\cli.mjs'
```

El `exports` del paquete tiene una regla `"./*.js": "./*.mjs"` que reescribe la
petición hacia un fichero que no existe (el real es `bin/cli.js`, en `.js`). La
salida es resolver el `package.json` y leer su campo `bin`:

```js
function rutaDelCli() {
  const manifiesto = requiere.resolve('openapi-typescript/package.json');
  const { bin } = requiere(manifiesto);
  const entrada = typeof bin === 'string' ? bin : bin?.['openapi-typescript'];
  ...
  return resolve(dirname(manifiesto), entrada);
}
```

**El shim de `node_modules/.bin` se evita a propósito.** En Windows es un `.cmd`,
que obliga a hacer `spawn` con `shell: true`, y con shell hay que empezar a
preocuparse por cómo se escapan las rutas. La raíz de este proyecto tiene
espacios **y** paréntesis en el nombre, así que es un problema real y no
hipotético. Se invoca el `.js` directamente con `process.execPath`, el mismo Node
que corre el script:

```js
spawnSync(process.execPath, [cli, ESPECIFICACION, '-o', destino], {
  cwd: RAIZ,
  encoding: 'utf8',
});
```

El temporal se crea con `mkdtempSync(join(tmpdir(), 'verifica-contrato-'))` y se
borra en un `finally`, para que un fallo no deje basura.

### 4. Enganchar los scripts

En `packages/contrato/package.json`, dos cambios y no uno:

```json
"comprobar": "node scripts/verifica.mjs && tsc --noEmit",
"verifica:contrato": "node scripts/verifica.mjs"
```

El segundo es el comando suelto, para CI o para lanzarlo a mano. El primero es el
que importa de verdad: `comprobar` ya era **el** comando del paquete, el que
cualquiera ejecuta sin pensar, así que es ahí donde el guardarraíl 2 tiene que
estar para que nadie se lo salte por olvido.

El `&&` corta en seco: si el contrato y los tipos no coinciden, `tsc` ni se
ejecuta. Es lo correcto — comprobar tipos que ya sabes que están desfasados solo
produce ruido, o peor, un verde que engaña.

Y en la raíz, delegando en el workspace, para que funcione desde cualquier sitio:

```json
"verifica:contrato": "npm run verifica:contrato -w @tramitador/contrato"
```

`scripts/` no se linta: `eslint.config.js` solo mira `**/*.{ts,tsx}`.

## Cómo verificar

### 0. El estado limpio

```bash
npm run comprobar -w @tramitador/contrato
npm run verifica:contrato
npm run lint
```

Los dos primeros imprimen la misma línea (`comprobar` la hereda del encadenado);
`lint` no imprime nada. Los tres salen con código `0`.

```
✔ src/tipos.gen.ts coincide con lo que genera openapi.yaml.
```

Que pasen en verde no demuestra nada todavía: un guardarraíl que nunca ha saltado
es un guardarraíl que no sabes si funciona. Lo que sigue es la prueba de verdad.

### 1. Romperlo: un estado nuevo solo en el YAML

Añade `- archivada` al enum `Estado` de `openapi.yaml`, y **no regeneres**:

```yaml
    Estado:
      enum:
        - borrador
        - enviada
        - aprobada
        - rechazada
        - archivada     # <- solo aquí
```

Los **dos** comandos fallan:

```bash
npm run comprobar -w @tramitador/contrato   # exit 1
npm run verifica:contrato                   # exit 1
```

...pero por el mismo motivo, y conviene verlo: los dos imprimen el mismo mensaje,
porque en los dos casos quien lo produce es `verifica.mjs`. En `comprobar`, el
`&&` ha cortado antes de llegar a `tsc`.

El guardarraíl 1, el de las afirmaciones de tipo, **no ha participado**. No
podría: la unión de `tipos.gen.ts` sigue siendo la de antes, así que para el
compilador no hay ninguna inconsistencia que ver. Le toca en el punto siguiente.

```
✖ src/tipos.gen.ts no coincide con openapi.yaml.

  El contrato y los tipos generados se han desincronizado. Alguien ha
  tocado el YAML sin regenerar, o ha editado a mano el .gen.ts.

  Primera diferencia en la linea 152:

    esperado (regenerado)   "        Estado: \"borrador\" | \"enviada\" | \"aprobada\" | \"rechazada\" | \"archivada\";"
    encontrado (en el repo) "        Estado: \"borrador\" | \"enviada\" | \"aprobada\" | \"rechazada\";"

  Tamanos: regenerado 23741 bytes, en el repo 23727 bytes.

  Para arreglarlo, regenera y committea el resultado:

    npm run gen -w @tramitador/contrato

  Si el cambio del YAML anade o quita valores de un enum, revisa tambien
  las constantes ESTADOS / ACCIONES de src/index.ts.
```

Código de salida `1`.

### 2. Regenerar, y olvidarse de la constante

Haz caso al mensaje, pero solo a medias: regenera y **no toques `ESTADOS`**.

```bash
npm run gen -w @tramitador/contrato
npm run verifica:contrato       # ✔ vuelve a pasar: el YAML y el .gen.ts ya coinciden
```

Ahora `comprobar` sigue fallando, pero por otra razón: el guardarraíl 2 pasa, el
`&&` deja llegar a `tsc`, y es el 1 el que corta.

```bash
npm run comprobar -w @tramitador/contrato
```

```
✔ src/tipos.gen.ts coincide con lo que genera openapi.yaml.
src/index.ts(71,48): error TS2345: Argument of type 'string[]' is not assignable to parameter of type 'never'.
src/index.ts(141,43): error TS2344: Type 'FaltanEnLaConstante<"archivada">' does not satisfy the constraint 'true'.
```

Ese `✔` seguido de dos errores es la imagen exacta del reparto: el contrato y los
tipos ya están sincronizados, lo que sigue roto es el código escrito a mano.

La primera línea es la que ya daba `listaCompleta` desde el paso 6. La segunda es
la nueva, y es la única de las dos que dice **qué** valor falta.

Añade `'archivada'` al array `ESTADOS` y las dos desaparecen. Ese es el ciclo
completo que los dos guardarraíles fuerzan: *editar YAML → regenerar → actualizar
constante*, sin poder saltarse ningún paso.

### 3. La dirección contraria

Restaura el YAML y el `.gen.ts`, y ahora mete el valor fantasma en la constante:

```ts
export const ESTADOS = listaCompleta<Estado>()([
  'borrador', 'enviada', 'aprobada', 'rechazada',
  'archivada',   // ya no existe en el contrato
]);
```

```
src/index.ts(76,3): error TS2322:
  Type '"archivada"' is not assignable to type '"borrador" | "enviada" | "aprobada" | "rechazada"'.
```

También se corta, pero conviene ser honesto sobre **quién** lo corta: es el
constraint `L extends readonly U[]` de `listaCompleta`, que dispara antes y deja
la rama `SobranEnLaConstante` sin llegar a evaluarse. El mensaje es claro igual,
así que no es un problema, pero significa que esa rama hoy no se ejecuta nunca
por esta vía. Aislada sí funciona:

```ts
type Estado = 'borrador' | 'enviada';
const LISTA = ['borrador', 'enviada', 'archivada'] as const;
export type Prueba = Afirma<MismosValores<Estado, typeof LISTA>>;
```

```
error TS2344: Type 'SobranEnLaConstante<"archivada">' does not satisfy the constraint 'true'.
```

**Restaura los tres ficheros antes de seguir** (`openapi.yaml`, `src/tipos.gen.ts`
y `src/index.ts`) y vuelve a lanzar el bloque del punto 0.

## Decisiones tomadas que no estaban en el enunciado

**Comparar bytes y no AST.** Se podría parsear el YAML y el `.ts` y comparar
estructuras, lo que toleraría cambios cosméticos del generador. Pero la regla del
paquete es *"`tipos.gen.ts` no se toca a mano"*, y comparar bytes es literalmente
esa regla: una diferencia cosmética significa que alguien editó el fichero, que
es justo lo que se quiere detectar. El precio a pagar es que una subida de
versión de `openapi-typescript` que cambie el formato hará fallar el script hasta
que alguien regenere y committee — que es el comportamiento correcto, aunque
sorprenda la primera vez.

**Dejar `listaCompleta` donde estaba.** Lo nuevo se suma, no sustituye. Da dos
errores en vez de uno cuando falla, pero quitarlo dejaría el paquete dependiendo
de una sola comprobación, y la vieja es la que cubre la dirección "sobra un
valor" señalando **la línea exacta del array**.

**Los tipos marcadores son `interface` con un `unique symbol`.** Podrían ser
`type X = { __falta: V }` a secas. Con `unique symbol` no hay forma accidental de
construir un valor de ese tipo, así que no pueden colarse en código real por
error: solo existen para salir impresos en un mensaje del compilador.

**Dos scripts con el mismo nombre en vez de uno.** El de la raíz delega en el del
workspace. Cuesta una línea y evita tener que recordar desde qué directorio se
lanza.

## Lo que todavía no está

**Nada de esto corre solo.** No hay CI, ni hook de git, ni `prepare` que lo
dispare. Los comandos existen y funcionan, pero alguien tiene que escribirlos.

La buena noticia es que el encadenado del paso 4 deja el trabajo hecho: el día
que haya pipeline, **`npm run comprobar` es la única línea que hay que meter**, y
cubre los dos guardarraíles en el orden correcto. `verifica:contrato` por
separado sigue siendo útil para un hook de `pre-commit`, donde no siempre
interesa pagar el `tsc` entero.

**Solo cubre los dos enums.** `ESTADOS` y `ACCIONES` son las únicas constantes de
runtime del paquete. Si mañana aparece un tercer enum en el YAML, el guardarraíl
1 no lo pedirá: hay que acordarse de escribir la constante *y* su afirmación. Un
generador que emitiera las constantes junto a los tipos cerraría eso del todo, a
costa de que `index.ts` deje de ser código escrito a mano.

**El guardarraíl 2 regenera de verdad, y eso cuesta.** Unos 90 ms más el arranque
de Node. Irrelevante en CI, notable si alguien lo pusiera en un hook de
`pre-commit` que se dispara en cada commit.

**`SobranEnLaConstante` es defensivo.** Como se vio en la verificación 3, hoy es
inalcanzable por la vía normal. Se mantiene porque cubre el caso de que alguien
retire `listaCompleta` en un refactor futuro. Si se prefiere no mantener código
que no se ejecuta, la rama se puede quitar y dejar solo unión → constante.

## Siguiente paso

El contrato ya no se puede desincronizar en silencio. Lo que sigue siendo cierto
es lo que cerraba `6. TIPOS.md`: **nadie importa el contrato todavía**. El primer
consumidor real —un backend que implemente las rutas de `5. RUTAS.md` y haga un
`res.json(...)` que tenga que encajar con `Solicitud`— es lo que dirá si el
contrato estaba bien pensado. Estos guardarraíles solo garantizan que, cuando
llegue, lo que lea sea verdad.
