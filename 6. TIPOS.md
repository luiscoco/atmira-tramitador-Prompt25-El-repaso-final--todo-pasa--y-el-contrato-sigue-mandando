# Tipos en `tramitador` — del YAML al compilador

El contrato ya describía una API completa (ver `5. RUTAS.md`), pero seguía siendo
un documento: nada impedía que el backend devolviera `estado: "pendiente"` ni que
el frontend leyera `solicitud.fecha`. Este paso convierte el YAML en tipos que el
compilador puede hacer cumplir, y expone `packages/contrato` para que
`import '@tramitador/contrato'` por fin funcione.

Dos cosas salen de aquí, y conviene no confundirlas:

- **Tipos** generados automáticamente desde `openapi.yaml`. Desaparecen al compilar.
- **Constantes** escritas a mano (`ESTADOS`, `ACCIONES`). Existen en tiempo de ejecución.

La sección "Tipos y constantes: dónde está la frontera" explica por qué hacen
falta las dos.

## Qué hay

```
packages/contrato/openapi.yaml     (ya existía; es la fuente de verdad)
packages/contrato/package.json     -> "gen", exports a src/index.ts, sin build
packages/contrato/tsconfig.json    -> solo comprobación (noEmit), no emite nada
packages/contrato/src/tipos.gen.ts -> GENERADO. No se toca a mano. 649 líneas
packages/contrato/src/index.ts     -> escrito a mano. Nombres cómodos + constantes
```

La regla del paquete cabe en una línea: **`tipos.gen.ts` se regenera, `index.ts`
se escribe**. Todo lo que quieras que sobreviva a un `npm run gen` va en `index.ts`.

Lo que exporta `index.ts`:

| Nombre | Qué es | ¿Existe en runtime? |
| --- | --- | --- |
| `Estado` | unión `'borrador' \| 'enviada' \| 'aprobada' \| 'rechazada'` | No |
| `Accion` | unión `'enviar' \| 'aprobar' \| 'rechazar'` | No |
| `Solicitud` | objeto completo que devuelve la API | No |
| `NuevaSolicitud` | cuerpo de `POST /solicitudes` | No |
| `PeticionTransicion` | cuerpo de `POST /solicitudes/{id}/transiciones` | No |
| `Tipo` | entrada del catálogo de tipos | No |
| `Operador` | operador de back-office | No |
| `ErrorApi` | cuerpo de cualquier respuesta de error | No |
| `ESTADOS` | array `readonly ['borrador', ...]` | **Sí** |
| `ACCIONES` | array `readonly ['enviar', ...]` | **Sí** |

## Los pasos que se siguieron

### 1. Leer lo que ya había antes de escribir nada

Tres cosas del repo condicionaban el diseño, y las tres se comprobaron primero:

- `tsconfig.base.json` tiene `verbatimModuleSyntax` e `isolatedModules`. Eso
  obliga a reexportar los tipos con `export type`, no con `export` a secas.
- `eslint.config.js` ya ignoraba `**/*.gen.ts`, con el comentario exacto de por
  qué: *"se regeneran, no se revisan ni se corrigen a mano"*. O sea que la
  decisión de no lintar el generado ya estaba tomada en el paso 3; aquí solo se
  aprovecha.
- `apps/backend/package.json` y `apps/frontend/package.json` ya declaraban
  `"@tramitador/contrato": "*"`, pero el paquete no tenía `main`. El enlace
  existía y el import fallaba.

### 2. Escribir el `package.json` sin paso de build

```json
"main": "./src/index.ts",
"types": "./src/index.ts",
"exports": { ".": "./src/index.ts" },
"scripts": { "gen": "openapi-typescript openapi.yaml -o src/tipos.gen.ts" },
"devDependencies": { "openapi-typescript": "^7.9.1" }
```

`main` y `exports` apuntan **al fuente TypeScript**, no a un `dist/`. Quien lo
consume ya sabe leer `.ts`: `tsx` en el backend, Vite en el frontend. Un paquete
que solo son tipos y dos arrays no gana nada montando un `tsc` + `dist/`; lo único
que consigue es un artefacto más que se puede quedar obsoleto respecto al fuente.

`openapi-typescript` va como **devDependency** y no como dependency porque solo
hace falta para *escribir* `tipos.gen.ts`. Nadie que importe el contrato en
producción necesita el generador: el fichero generado ya está ahí.

### 3. Generar los tipos

Desde la raíz del monorepo:

```bash
npm install
npm run gen --workspace @tramitador/contrato
```

O, equivalentemente, desde `packages/contrato`: `npm run gen`.

```
added 26 packages, changed 3 packages, and audited 141 packages in 4s
found 0 vulnerabilities

> @tramitador/contrato@0.0.0 gen
> openapi-typescript openapi.yaml -o src/tipos.gen.ts

✨ openapi-typescript 7.13.0
🚀 openapi.yaml → src/tipos.gen.ts [43.9ms]
```

Los 26 paquetes son el generador y sus dependencias, todos de desarrollo. Ninguna
dependencia de negocio ha entrado en el monorepo todavía.

El resultado son 649 líneas con tres bloques: `paths` (una entrada por ruta),
`components` (los ocho esquemas) y `operations` (una entrada por `operationId`).
Los enums se generan como uniones de literales, que es justo lo que interesa:

```ts
Estado: "borrador" | "enviada" | "aprobada" | "rechazada";
Accion: "enviar" | "aprobar" | "rechazar";
```

Y `nullable: true` se traduce fielmente: `operador: string | null`. El contrato
decía que un `operador` ausente es `null`, no que el campo falte, y el tipo lo
respeta.

### 4. Ponerle nombres cómodos en `index.ts`

Lo que genera la herramienta es correcto pero incómodo de escribir: todo cuelga de
`components['schemas'][...]`. El barril lo aplana:

```ts
import type { components } from './tipos.gen';

type Esquemas = components['schemas'];

export type Estado = Esquemas['Estado'];
export type Solicitud = Esquemas['Solicitud'];
// ...
```

El import es `'./tipos.gen'`, **sin extensión**, porque `moduleResolution` es
`"bundler"` en el base (escribir `./tipos.gen.ts` exigiría activar
`allowImportingTsExtensions`, y `./tipos.gen.js` sería mentir sobre un fichero que
no existe).

Un solo nombre cambia respecto al contrato: el esquema `Error` se exporta como
**`ErrorApi`**. Si se llamara `Error`, cualquier fichero que lo importara taparía
el `Error` global de JavaScript — justo en los ficheros donde más se escribe
`throw new Error(...)`. Es un choque silencioso y desagradable, y renombrarlo aquí
cuesta cero.

### 5. Añadir las dos constantes de runtime

Aquí está el motivo real de que `index.ts` exista:

```ts
export const ESTADOS  = listaCompleta<Estado>()(['borrador','enviada','aprobada','rechazada']);
export const ACCIONES = listaCompleta<Accion>()(['enviar','aprobar','rechazar']);
```

`listaCompleta` es un ayudante de cuatro líneas cuyo único cometido es que estos
arrays no se queden atrás cuando cambie el contrato:

```ts
const listaCompleta =
  <U extends string>() =>
  <const L extends readonly U[]>(
    valores: L & ([Exclude<U, L[number]>] extends [never] ? unknown : never),
  ): L => valores;
```

Hace tres cosas a la vez:

1. **Exige que estén todos** los valores de la unión. Si falta uno, el tipo del
   parámetro se colapsa a `never` y no compila.
2. **Prohíbe valores que no estén** en la unión (un `'pendiente'` de más falla).
3. **Conserva los literales**: el tipo resultante es la tupla
   `readonly ['borrador', 'enviada', ...]`, no `string[]`.

El punto 1 es el que importa a largo plazo. Si mañana `openapi.yaml` gana un
estado, `npm run gen` lo mete en la unión y **el proyecto deja de compilar** hasta
que se añada también al array. Sin ese guardarraíl, el array se quedaría corto en
silencio y el backend seguiría rechazando con `400` un estado que el contrato ya
considera válido — un bug que no da la cara hasta producción.

### 6. Añadir un `tsconfig.json` al paquete

No estaba en el enunciado, pero `packages/contrato` era el único workspace sin
`tsconfig.json`, y sin él no hay manera de comprobar los tipos ni de que el editor
entienda el fichero. Lleva `"noEmit": true`: **no es un paso de build**, es una
comprobación. Y `"lib": ["ES2022"]` con `"types": []`, sin DOM y sin Node, porque
el contrato son tipos y dos arrays de strings: si alguien mete un `fetch` aquí,
que falle al compilar.

Va acompañado de un script `"comprobar": "tsc --noEmit"`.

## Cómo verificar

### 1. Que compila

```bash
npx tsc --noEmit -p packages/contrato/tsconfig.json
```

Sin salida y código de salida `0`.

### 2. Que el guardarraíl de sincronía funciona de verdad

La prueba que importa: borra a mano `'rechazada'` del array `ESTADOS` y vuelve a
compilar.

```
packages/contrato/src/index.ts(71,48): error TS2345:
  Argument of type 'string[]' is not assignable to parameter of type 'never'.
```

Ese `'never'` es el mensaje que verás el día que el contrato crezca y olvides
actualizar el array. Es críptico, sí; por eso el comentario que hay justo encima
de `listaCompleta` en el código lo anticipa.

Restaura el valor y vuelve a compilar antes de seguir.

### 3. Que las constantes existen y los tipos no

Esta es la demostración de la sección siguiente, y se puede ejecutar:

```bash
node --experimental-strip-types -e "import('./packages/contrato/src/index.ts').then(m => console.log(m.ESTADOS, m.ACCIONES, Object.keys(m)))"
```

```

```

Fíjate en `exports`: los ocho tipos exportados **no aparecen**. Node ha quitado los

### 4. Que el lint sigue limpio

```bash

```

Sin salida. Las 649 líneas generadas no se lintan, por el `**/*.gen.ts` que ya
estaba en `eslint.config.js`.

## Tipos y constantes: dónde está la frontera

**Un tipo de TypeScript no llega a existir.** `Estado` no es un objeto, ni una
variable, ni una entrada en ninguna tabla. Es una anotación que el compilador usa
para revisar tu código y después **borra**. El JavaScript que se ejecuta no tiene
ni rastro de él. Por eso esto ni siquiera compila:

```ts
if (Estado.includes(x))    // ❌ 'Estado' solo se refiere a un tipo, pero aquí se usa como valor
for (const e of Estado)    // ❌ lo mismo
```

**Una constante sí existe.** `ESTADOS` es un array de strings de verdad: ocupa
memoria, se recorre, se serializa a JSON, se le puede llamar `.includes()`. La
verificación 3 de arriba es la prueba: los tipos no aparecen en los exports del
módulo cargado, los arrays sí.

### Por qué el backend necesita las constantes

Porque el backend recibe datos **de fuera**, y de fuera no viene ningún tipo: viene
texto.

Cuando llega `GET /api/solicitudes?estado=pendiente`, lo que el framework entrega
en `req.query.estado` es la cadena `"pendiente"`. TypeScript no puede decir nada
útil ahí: al compilar no sabe qué mandará el cliente, y al ejecutar ya no está para
opinar. El contrato dice que ese parámetro debe pertenecer al enum `Estado` y que
si no, se responde `400` — y esa comprobación ocurre con un cliente real al otro
lado, que es exactamente el momento en el que los tipos ya no existen:

```ts
import { ESTADOS, type Estado } from '@tramitador/contrato';

const estado = req.query.estado;
if (estado !== undefined && !ESTADOS.includes(estado as Estado)) {
  return res.status(400).json({
    mensaje: 'El filtro de estado no es valido.',
    // Y aquí el array hace falta otra vez: para redactar el mensaje.
    detalle: `Valor recibido: '${estado}'. Valores admitidos: ${ESTADOS.join(', ')}.`,
  });
}
// A partir de aquí TypeScript ya sabe que `estado` es un Estado.
```

Nótese el detalle: el `detalle` que pide el contrato enumera literalmente los
valores admitidos (`borrador, enviada, aprobada, rechazada`). Eso es
`ESTADOS.join(', ')`. Con un tipo no se puede generar ese texto; con el array sale
gratis y nunca se desincroniza del contrato.

Lo mismo ocurrirá con `ACCIONES` al validar el cuerpo de
`POST /solicitudes/{id}/transiciones`, y volverá a ocurrir en el frontend: el
desplegable de filtro por estado se pinta con `ESTADOS.map(...)`, y un `<option>`
por estado necesita valores reales, no una unión de literales.

**La regla corta:** los tipos protegen el código que escribes tú; las constantes
protegen el código frente a lo que llega de fuera. En la frontera — query params,
cuerpos, mensajes de error, menús de la interfaz — siempre hacen falta las segundas.

## Decisiones tomadas que no estaban en el enunciado

**`ErrorApi` en vez de `Error`.** Por el choque con el global de JavaScript. El
contrato sigue llamándolo `Error`; el renombrado vive solo en el barril.

**`tsconfig.json` con `noEmit` en el paquete.** Era el único workspace sin él.
No contradice el "sin paso de build": no emite nada.

**`listaCompleta` en vez de `as const satisfies readonly Estado[]`.** El `satisfies`
comprueba que cada elemento pertenece a la unión, pero **no** que estén todos: un
array al que le falte un estado pasa el `satisfies` sin rechistar. Como el riesgo
real aquí es que el contrato crezca y los arrays se queden atrás, se eligió la
versión que rompe la compilación. El precio es un genérico algo denso y un mensaje
de error críptico.

**`"private": true` y `"files"` en el paquete.** `1. MONOREPO.md` lo había dejado
publicable a propósito, pero ahora que `exports` apunta a `.ts` publicarlo a un
registro no funcionaría tal cual. Se marca privado; si algún día se publica, ese
será el momento de discutir si hace falta un `dist/`.

## Lo que todavía no está

**Nadie importa el contrato aún.** `apps/backend` y `apps/frontend` lo declaran
como dependencia, pero no tienen un solo fichero `.ts`. Que el import funcione de
verdad no se ha comprobado desde un consumidor real.

**No hay validación en runtime de los objetos completos.** `ESTADOS` y `ACCIONES`
cubren los dos enums, pero nada comprueba que un cuerpo entrante tenga la forma de
`NuevaSolicitud`. Eso pide un validador de esquemas (Zod, Ajv contra el propio
YAML...) y es una decisión aparte.

**`npm run gen` no está enganchado a nada.** Es manual. Si alguien edita
`openapi.yaml` y no lo ejecuta, `tipos.gen.ts` queda desfasado sin que nadie avise.
Un `prepare`, un hook de git o un paso de CI que regenere y compruebe que no hay
diff lo cerraría.

**Los `format` del YAML se pierden.** `format: uuid` y `format: date-time` generan
`string` a secas, igual que `pattern: '^SOL-\d{4}-\d{4}$'`. El compilador no
distingue un `id` de una `referencia` de un `creadaEn`: los tres son `string` y son
intercambiables por error. Tipos de marca (*branded types*) lo arreglarían, a costa
de fricción en cada construcción de objeto.

## Siguiente paso

El contrato ya es código. Lo que falta es el primer consumidor: un backend que
importe `Solicitud` y `ESTADOS`, implemente las cinco rutas de `5. RUTAS.md` y
demuestre que los tipos generados encajan con lo que de verdad se escribe en un
`res.json(...)`. Ahí es donde se verá si el contrato estaba bien pensado.
