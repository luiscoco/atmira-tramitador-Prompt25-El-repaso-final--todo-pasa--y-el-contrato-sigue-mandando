# El cliente de API — un `fetch` en todo el frontend

`17. FRONTEND.md` cerró su sección "Lo que todavía no está" con dos frases que
apuntaban al mismo sitio:

> **El `as Solicitud[]` de `App.tsx` no valida nada.** [...] Es la costura donde
> los tipos dejan de comprobarse solos.

> **El estado vive en un `useState` del componente raíz.** Sirve para una
> pantalla y para una llamada. En cuanto haya filtros, creación y
> transiciones —las otras seis operaciones del contrato— hará falta decidir
> dónde vive el estado del servidor.

Este paso no resuelve ninguna de las dos, pero es el que hay que dar antes: el
momento de decidir **dónde vive la llamada a la API** es justo antes de escribir
la segunda, no después de la quinta. Hoy hay una sola —el `fetch` de
`App.tsx`— y todavía se puede poner la costura en un único fichero sin refactor.

```
apps/frontend/src/api/cliente.ts   NUEVO  <- el único fetch de la aplicación
```

No se ha tocado nada más. Ni el backend, ni `vite.config.ts`, ni los
`package.json`. `App.tsx` **sigue con su `fetch` propio** y eso es deliberado:
ver el paso 11.

## Qué hay

| Export | Qué es |
| --- | --- |
| `ErrorDeApi` | La respuesta que no salió bien: `status`, `message`, `detalle?` |
| `pedir<T>(ruta, opciones?)` | La única llamada a `fetch` de la aplicación |
| `listarSolicitudes(estado?)` | `GET /solicitudes[?estado=]` -> `readonly Solicitud[]` |
| `obtenerSolicitud(id)` | `GET /solicitudes/{id}` -> `Solicitud` |
| `listarTipos()` | `GET /tipos` -> `readonly Tipo[]` |
| `listarOperadores()` | `GET /operadores` -> `readonly Operador[]` |
| `crearSolicitud(nueva)` | `POST /solicitudes` -> `Solicitud` (201) |
| `transicionarSolicitud(id, accion)` | `POST /solicitudes/{id}/transiciones` -> `Solicitud` |

Seis de las siete operaciones del contrato. Falta `GET /api/salud`, que no la
pide ninguna pantalla: es una sonda para `curl` y para un healthcheck, no una
llamada de la aplicación.

La regla que ordena el fichero es la misma que ordena los scripts en
`16. ARRANQUE.md` y las rutas en `14. SOLICITUDES.md`: **cada cosa se escribe
una vez y en el sitio donde se sabe**. La pareja ruta/tipo se fija en las seis
funciones de conveniencia; el manejo de HTTP, en `pedir`; el resto de la
aplicación no vuelve a ver ni una URL ni un `respuesta.ok`.

## Los pasos que se siguieron

### 1. Leer el contrato antes de escribir una firma

Lo primero no fue abrir un editor, fue leer `packages/contrato/src/index.ts` y
`src/tipos.gen.ts`. De ahí salen las seis firmas sin inventarse nada:

| Del contrato | Se usa en |
| --- | --- |
| `Solicitud` | lo que devuelven cinco de las seis funciones |
| `NuevaSolicitud` (`tipo`, `solicitante`) | el parámetro de `crearSolicitud` |
| `PeticionTransicion` (`{ accion }`) | el cuerpo que monta `transicionarSolicitud` |
| `Estado` | el parámetro opcional de `listarSolicitudes` |
| `Accion` | el parámetro de `transicionarSolicitud` |
| `Tipo`, `Operador` | los dos catálogos |
| `ErrorApi` (`{ mensaje, detalle? }`) | el cuerpo que lee `ErrorDeApi` |

El detalle que importa es que `NuevaSolicitud` y `Solicitud` **no son el mismo
tipo**: el backend añade `id`, `referencia`, `estado`, `operador`, `creadaEn` y
`actualizadaEn`. Por eso `crearSolicitud` recibe uno y devuelve el otro, y no
hay ninguna tentación de reutilizar `Solicitud` como parámetro de entrada.

También de ahí sale el nombre `ErrorApi`, que el contrato reexporta así —y no
como `Error`— porque el global de JavaScript ya ocupa ese nombre. El fichero
lo importa con `import type`, obligatorio con el `verbatimModuleSyntax` que
`tsconfig.base.json` puso en el paso 2.

### 2. Leer las rutas del backend, no solo el YAML

El contrato dice qué existe; `apps/backend/src/rutas/solicitudes.ts` dice qué
pasa cuando algo va mal, y eso es lo que hay que documentar en los `@throws`.
Las cuatro rutas se leyeron enteras para anotar los códigos reales:

```
GET  /solicitudes           400 si `?estado=` no está en ESTADOS
GET  /solicitudes/:id       400 si el id no tiene forma de UUID
                            404 si no existe
POST /solicitudes           400 si falta `tipo` o `solicitante`
POST /solicitudes/:id/...   400 id mal formado · 404 no existe · 409 transición ilegal
```

El orden `404` antes que `409` que `5. RUTAS.md` razonó —contestar `409` sobre
una solicitud que no existe confirma que ese id es real— no se reimplementa
aquí, pero sí se menciona en el JSDoc de `transicionarSolicitud`, porque es lo
que explica por qué esos dos códigos nunca llegan juntos.

### 3. `ErrorDeApi`: clase, no `type` suelto

El enunciado pedía "un tipo `ErrorDeApi` (`status`, `message`, `detalle?`)". Se
escribió como **clase que extiende `Error`**, con esos tres miembros exactos.
Es la única desviación de la letra del enunciado y tiene dos motivos, los dos
visibles en el sitio donde se usa —un `catch`, donde lo que llega es `unknown`—:

- **`instanceof` estrecha el tipo.** Con un objeto plano lanzado con `throw`,
  cada `catch` de la aplicación tendría que escribir su propio predicado para
  poder leer `.status`.
- **Hereda `message` y `stack`.** Cae de pie en todo lo que ya trata errores: el
  `fallo instanceof Error` que `App.tsx` ya tiene escrito, el `console.error`
  del navegador, un error boundary de React.

Que el campo se llame `message` y no `mensaje` deja de ser una incoherencia en
un fichero por lo demás en castellano: es el `message` de `Error`. El `mensaje`
del cuerpo del contrato se vuelca ahí dentro.

Dos detalles pequeños del constructor:

```ts
this.name = 'ErrorDeApi';
```

Sin esta línea, un `ErrorDeApi` se imprime como `"Error"` en la consola y en
cualquier log, porque `name` se hereda del padre.

```ts
if (detalle !== undefined) {
  this.detalle = detalle;
}
```

Asignar siempre crearía la propiedad igualmente, y entonces `'detalle' in fallo`
contestaría `true` sobre un error que no tiene detalle.

### 4. `pedir<T>()`: el prefijo `/api` lo pone la función

Las seis funciones pasan la ruta **sin** `/api`:

```ts
return pedir<Solicitud[]>(`/solicitudes${consulta}`, opciones);
```

El prefijo es una constante del módulo y se concatena en un único punto. No es
cosmética: es el mismo `servers: [{ url: /api }]` de `openapi.yaml` que obliga
al backend a registrar sus rutas con el prefijo incluido y que el proxy de
`vite.config.ts` no reescribe (`17. FRONTEND.md`, paso 3). Escrito una vez, no
hay forma de que una de las seis se lo olvide.

Y sigue sin aparecer ningún host ni ningún puerto. Toda la argumentación del
proxy —un origen, ni CORS ni `VITE_API_URL`— se apoya en que la URL del cliente
sea relativa, y este fichero es ahora el único sitio donde se podría romper.

### 5. Las cabeceras, después del spread

```ts
const respuesta = await fetch(BASE + ruta, {
  ...opciones,
  headers: {
    Accept: 'application/json',
    ...opciones?.headers,
  },
});
```

El `...opciones` de la primera línea copiaría `headers` **entera**, así que hay
que reconstruirla aparte: si no, quien pase una cabecera propia se lleva por
delante el `Accept`. Dentro, el orden es el contrario —`Accept` primero, lo de
`opciones` después— para que quien llama pueda sobrescribirla si de verdad lo
necesita. La misma estructura se repite en `crearSolicitud` y
`transicionarSolicitud` con el `Content-Type`.

### 6. El cuerpo del error, dentro de un `try`

El contrato promete que todo error trae `{ mensaje, detalle? }`. Esa promesa
**solo cubre al backend**: un `502` del proxy, la página de error de un
balanceador o una respuesta cortada a la mitad llegan por el mismo camino y no
son JSON. De ahí que `comoError` envuelva el `json()`:

```ts
const porDefecto = `La API ha respondido ${respuesta.status}.`;
```

Si el cuerpo no se puede leer, el error se construye con el `status`, que es lo
único que se sabe con certeza. Y cuando sí se lee, cada campo se comprueba con
`typeof` y no con `??`:

```ts
const mensaje = typeof cuerpo.mensaje === 'string' ? cuerpo.mensaje : porDefecto;
```

`??` solo descarta `null` y `undefined`. El cuerpo viene de la red y puede ser
un número, un array o un objeto anidado, y nada de eso se puede enseñar como
mensaje. Es el mismo razonamiento que hace el backend con `peticion.body` en
`14. SOLICITUDES.md`, en la dirección contraria.

### 7. `?estado=` vacío no es lo mismo que no mandar query

```ts
const consulta =
  estado === undefined ? '' : `?${new URLSearchParams({ estado }).toString()}`;
```

La comparación es con `undefined` y no un `if (!estado)`, y la rama de "sin
filtro" pide la ruta **limpia**. El motivo está al otro lado: el backend trata
`?estado=` como un filtro escrito mal y contesta `400`, no como un filtro
ausente. Un `listarSolicitudes()` que montara la query siempre produciría un
error en el caso más común de todos.

El valor se monta con `URLSearchParams` y no concatenando, que es quien se ocupa
de escapar lo que haga falta. Hoy los estados son cuatro palabras sin sorpresas;
la URL se construye igual el día que dejen de serlo.

### 8. `encodeURIComponent` en los `id`

```ts
`/solicitudes/${encodeURIComponent(id)}`
```

El `id` es un UUID y un UUID no tiene nada que escapar, así que la llamada no
cambia el resultado en ningún caso real. Está por lo mismo que el
`URLSearchParams` del paso anterior: el que interpola un valor en una URL sin
escaparlo no se entera hasta que llega el valor que sí lo necesitaba.

Si el `id` viene mal formado, quien lo rechaza es el backend con un `400`, antes
incluso de mirar los datos. El cliente no duplica esa validación: sería la
tercera copia de la misma regla.

### 9. `opciones?` en las seis, por el `AbortController`

Todas las funciones de conveniencia arrastran un `opciones?: RequestInit` final.
Existe sobre todo para una cosa:

```ts
const control = new AbortController();
listarSolicitudes(undefined, { signal: control.signal });
```

Cancelar la petición cuando el componente se desmonta es lo normal en un
`useEffect` —y `StrictMode` lo exige, como razonó `17. FRONTEND.md`—. Sin este
parámetro, el primer componente que necesitara un `signal` tendría que saltarse
el cliente y volver a escribir un `fetch` a mano, que es exactamente lo que este
fichero viene a evitar.

### 10. `readonly` en las listas

```ts
export function listarTipos(opciones?: RequestInit): Promise<readonly Tipo[]>
```

Las tres funciones que devuelven listas las devuelven `readonly`. Nadie tiene
por qué ordenar, filtrar en el sitio o hacer `push` sobre la respuesta de la API
en el mismo punto donde la recibe: si hace falta una lista distinta, se deriva
una nueva. Encaja además con el `readonly Solicitud[]` que el tipo `Carga` de
`App.tsx` ya declaraba.

### 11. El obstáculo: `tsc --noEmit` ya fallaba antes de escribir nada

Al comprobar el fichero:

```
src/api/cliente.ts(41,8): error TS2307: Cannot find module '@tramitador/contrato'
src/App.tsx(9,32):        error TS2307: Cannot find module '@tramitador/contrato'
```

La segunda línea es la que da el diagnóstico: `App.tsx` no se había tocado, así
que el error **no era del código nuevo**. La comprobación siguiente lo confirmó
—el backend falla igual, en sus ocho ficheros— y localizó el problema en el
enlace de workspace, no en el import:

```
node_modules/@tramitador/contrato    aparece como directorio, no como symlink
```

`packages/contrato/package.json` apunta `main`, `types` y `exports` al **fuente
TypeScript**, sin paso de build. Eso funciona mientras el enlace del workspace
sea un symlink de verdad; con una copia o un junction, TypeScript no resuelve el
`exports` hasta el `.ts`.

Para verificar el fichero nuevo sin esperar a que eso se arregle, se hizo un
type-check aislado con un `paths` temporal apuntando al fuente (ver "Cómo
verificar"). El resultado: limpio. El fallo de resolución es previo, afecta al
monorepo entero y se arregla con un `npm install` en la raíz — no con un cambio
en este fichero.

Ese mismo obstáculo es la razón de que **`App.tsx` no se haya migrado** todavía
a usar el cliente. Cambiarlo ahora significaría tocar un fichero que no se puede
comprobar de extremo a extremo, y mezclar en el mismo paso "el cliente existe"
con "la pantalla lo usa". Son dos cambios y son dos pasos.

## Cómo verificar

### 1. El type-check del fichero, aislado

Mientras el enlace del workspace siga roto (paso 11), el `npm run comprobar` del
frontend no sirve para verificar nada. El sustituto es un `tsconfig` temporal que
hereda el del workspace —o sea, todas las reglas de `tsconfig.base.json`— y solo
añade la ruta al fuente del contrato:

```jsonc
// apps/frontend/tsconfig.tmp.json
{
  "extends": "./tsconfig.json",
  "compilerOptions": {
    "baseUrl": ".",
    "paths": { "@tramitador/contrato": ["../../packages/contrato/src/index.ts"] }
  },
  "include": ["src/api/cliente.ts"]
}
```

```bash
cd apps/frontend
npx tsc -p tsconfig.tmp.json --noEmit
rm tsconfig.tmp.json
```

Sin salida y código de salida `0`. Lo que se comprueba así es todo lo que
importa del fichero: que las seis firmas encajan con los tipos del contrato, y
que `strict`, `noUncheckedIndexedAccess` y `verbatimModuleSyntax` no tienen nada
que decir.

### 2. El lint

Este sí funciona tal cual, porque ESLint no resuelve imports de tipos:

```bash
npx eslint apps/frontend/src/api/cliente.ts
```

Sin salida. Lo que aquí se mira de verdad es el `catch {}` sin parámetro de
`comoError`: la configuración de `3. LINT.md` tiene `caughtErrors: 'all'`, así
que un `catch (e)` con la `e` sin usar sería un error. La forma correcta es no
declararla.

### 3. Que el enlace del workspace es lo único que falta

```bash
cd apps/backend && npx tsc --noEmit
```

Si el backend —que este paso no ha tocado— falla con el mismo `TS2307`, el
problema es del `node_modules` y no del cliente. Es la comprobación de una línea
que separa "he escrito algo mal" de "el install está a medias", y es la que hay
que hacer antes de tocar ningún import.

### 4. Contra el backend arrancado (opcional)

Con los dos servidores levantados (`npm run dev` y `npm run dev:frontend`, en
dos terminales, como explica `17. FRONTEND.md`), desde la consola del navegador
en `http://localhost:5173`:

```js
const { listarSolicitudes, transicionarSolicitud, ErrorDeApi } =
  await import('/src/api/cliente.ts');

(await listarSolicitudes()).length;             // 12
(await listarSolicitudes('aprobada')).length;   // las aprobadas

try {
  await transicionarSolicitud('no-es-un-uuid', 'aprobar');
} catch (e) {
  e instanceof ErrorDeApi;   // true
  e.status;                  // 400
  e.message;                 // el `mensaje` del backend, no "Failed to fetch"
}
```

La tercera parte es la que importa: comprueba a la vez que el error del backend
llega entero hasta el `catch`, que `instanceof` funciona y que `status` está
donde se dijo.

## Decisiones tomadas que no estaban en el enunciado

**`ErrorDeApi` es una clase.** Explicado en el paso 3. Es la única desviación de
la letra del enunciado, y los tres miembros que pedía están exactamente donde
decía.

**`pedir` se exporta.** El enunciado no dice si es interna. Se exporta porque
hace falta el día que aparezca una ruta que el cliente no cubra —o una llamada
puntual desde un test—, pero el JSDoc dice explícitamente que la aplicación debe
usar las envolturas: son ellas las que fijan la pareja ruta/tipo en un sitio.

**Un `opciones?` en las seis funciones.** El enunciado solo listaba los
parámetros de negocio. Sin este, el primer `useEffect` que necesite cancelar una
petición se salta el cliente entero (paso 9).

**`Accept: application/json` en todas las peticiones.** El backend contesta JSON
haga lo que haga, así que hoy no cambia nada. Está por honestidad del cliente:
la cabecera dice lo que `pedir` va a hacer con la respuesta dos líneas más
abajo, que es llamar a `json()`.

**`GET /api/salud` no tiene función.** Es una sonda, no una operación de la
aplicación. Añadirla sería dar a entender que alguna pantalla la necesita.

**Las listas salen `readonly`.** El contrato no dice nada de mutabilidad; es una
decisión del cliente (paso 10).

**No se ha tocado `App.tsx`.** Explicado al final del paso 11: el cliente y su
primer consumidor son dos cambios distintos, y el segundo no se puede verificar
hasta que el enlace del workspace esté arreglado.

## Lo que todavía no está

**Sigue sin haber validación en runtime.** El `as T` de `pedir` es el mismo acto
de fe que el `as Solicitud[]` de `App.tsx`; lo único que ha cambiado es que
ahora está escrito **una vez** y no una por llamada. Eso es exactamente lo que
hacía falta para poder cerrarlo: meter un validador (zod, valibot) es cambiar
una línea de este fichero, no auditar el árbol de componentes. Lo que no se ha
decidido es qué hacer cuando la API incumple su propio contrato, y esa sigue
siendo una decisión de diseño.

**`App.tsx` todavía llama a `fetch` a mano.** Mientras no se migre, hay dos
caminos a la API en la aplicación y este fichero no es "el único `fetch`" más
que en el título.

**No hay tests del cliente.** Siguen faltando las dos piezas que
`17. FRONTEND.md` ya anotaba —un entorno DOM y una librería de render—, aunque
para este fichero no harían falta: se prueba con un `fetch` falso. Los casos que
merecen uno están claros (un `500` con cuerpo JSON, un `502` sin cuerpo, el
`?estado=` que no se manda), pero ninguno está escrito.

**Nada cancela ni deduplica peticiones por su cuenta.** El cliente acepta un
`signal`, pero quien lo crea y lo aborta sigue siendo el componente. No hay
caché, ni reintento, ni invalidación tras un `POST`: la decisión sobre dónde
vive el estado del servidor sigue abierta, igual que la dejó el paso anterior.

**`operador` sigue sin escribirse desde ningún sitio.** Ahora hay un
`listarOperadores()` tipado que nadie puede usar para asignar nada, porque no
existe la operación en el contrato. El hueco no se mueve de `openapi.yaml`.

## Siguiente paso

Arreglar el enlace del workspace y, con `tsc --noEmit` volviendo a pasar en los
tres paquetes, migrar `App.tsx` a `listarSolicitudes()`. Es el cambio que
convierte este fichero en lo que dice ser y el que deja el `fetch` en un único
sitio de verdad.
