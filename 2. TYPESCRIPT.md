# TypeScript en `tramitador` — configuración base y por workspace

Segundo paso del monorepo (el primero está en [MONOREPO.md](MONOREPO.md)). Aquí se define
**cómo se compila**, todavía sin una sola línea de código de aplicación.

## Qué hay

```
tsconfig.base.json             (raíz, no compila nada: solo se hereda)
apps/backend/tsconfig.json     -> extends ../../tsconfig.base.json
apps/frontend/tsconfig.json    -> extends ../../tsconfig.base.json
```

La idea es que las reglas de rigor se decidan **una vez** en la raíz y ningún workspace
pueda relajarlas por descuido. Cada hijo añade solo lo que es específico de su entorno:
qué APIs existen (`lib`), qué `@types` se cargan, si emite JavaScript o no, y si hay JSX.

`tsconfig.base.json` no lleva `include` ni `files` a propósito. No es un proyecto
compilable, es una plantilla. Quien tiene entradas y salidas es cada app.

## Las banderas del base, una a una

Las tres primeras son las de siempre; el interés está en las cinco siguientes.

| Flag | Qué hace en la práctica |
|---|---|
| `target: "ES2022"` | Node 18+ y navegadores modernos. TS deja de transpilar `async/await`, campos de clase y `#private` a helpers: el JS emitido se parece al fuente y los stack traces son legibles. |
| `strict: true` | Paraguas de `strictNullChecks`, `noImplicitAny`, `strictFunctionTypes`… Lo que más se nota: `null` y `undefined` dejan de ser asignables a todo. |
| `noUnusedLocals` / `noUnusedParameters` | Error en variables e imports muertos. Para parámetros impuestos por una firma ajena, el escape es el prefijo `_`: `(_req, res) => …` no da error. |
| `noFallthroughCasesInSwitch` | Error si un `case` con cuerpo cae al siguiente sin `break`/`return`/`throw`. El fallthrough intencionado se sigue permitiendo apilando `case` vacíos, que es la forma legible de escribirlo. |
| `noUncheckedIndexedAccess` | Acceder por índice devuelve `T \| undefined` en vez de `T`. Sección propia más abajo. |
| `verbatimModuleSyntax` | Lo que escribes es lo que se emite: TS deja de adivinar qué imports son solo de tipos y borrarlos por su cuenta. Te obliga a marcar `import type { Foo }` cuando el símbolo solo se usa como tipo. |
| `isolatedModules` | Garantiza que cada fichero se puede transpilar **por separado**, sin ver el resto del proyecto — que es justo como trabajan esbuild, swc y Vite. Prohíbe lo que necesita información global: `const enum`, re-export de tipos sin `export type`, namespaces con valores. |
| `moduleResolution: "bundler"` | Resuelve imports como Vite/esbuild: lee `exports` del `package.json` (como Node) pero **no** exige escribir la extensión en los imports relativos (`./util`, no `./util.js`). |

`verbatimModuleSyntax` e `isolatedModules` van juntas por un motivo: ambas eliminan
la magia que TypeScript hace mirando el proyecto entero. Cuanto menos dependa el
significado de un fichero de sus vecinos, menos sorpresas al cambiar de bundler.

Además hay tres opciones de higiene que no se pidieron pero que se dan por supuestas:
`moduleDetection: "force"` (todo fichero es módulo, aunque aún no exporte nada),
`resolveJsonModule` y `skipLibCheck` (no revisar los `.d.ts` de terceros; no relaja
tu código, solo evita pagar los errores de otros).

## Qué cambia de verdad `noUncheckedIndexedAccess`

Es la bandera con más impacto diario, y la menos intuitiva:

```ts
const nombres: string[] = ["Ana"];
nombres[0].toUpperCase();
```

- **Sin el flag**: `nombres[0]` es `string`. Compila sin una queja.
- **Con el flag**: `nombres[0]` es `string | undefined` y la segunda línea **no compila**.

El matiz importante: TypeScript **no** está detectando que el índice se salga del array
— no hace ningún análisis de longitud. Es que el tipo `string[]` no contiene la
información de cuántos elementos hay, así que el elemento `0` es tan incierto como el
`3`. El flag simplemente deja de fingir lo contrario.

La forma correcta pasa a ser estrechar antes de usar:

```ts
const primero = nombres[0];
if (primero !== undefined) primero.toUpperCase();   // aquí ya es string
```

Tres aclaraciones que ahorran disgustos:

- **También afecta a las firmas de índice.** Con `Record<string, Usuario>`,
  `usuarios["ana"]` pasa a ser `Usuario | undefined`. Es exactamente el caso que más
  se rompe en producción.
- **No afecta a las claves declaradas.** En `{ nombre: string }`, `obj.nombre` sigue
  siendo `string`. El flag solo toca índices arbitrarios.
- **No afecta a la iteración ni a las tuplas.** `for (const n of nombres)` da `string`
  limpio, y en `const par: [string, string]` el `par[0]` es `string` sin `undefined`,
  porque ahí el tipo sí codifica la longitud.

Consecuencia práctica: el patrón `const primero = lista[0]` te obliga a decidir qué pasa
si la lista viene vacía, en vez de descubrirlo en runtime.

## Lo específico de cada app

### `apps/backend`

```jsonc
"lib": ["ES2022"],          // sin DOM: usar `window` o `document` es error de compilación
"types": ["node"],          // limita los @types autocargados (requiere @types/node)
"rootDir": "src", "outDir": "dist",
"declaration": true, "sourceMap": true
```

`types` merece una nota: si se omite, TypeScript carga **todo** lo que haya bajo
`node_modules/@types`, incluidos los tipos que solo instaló el otro workspace. Acotarlo
evita que el backend "vea" sin querer tipos de navegador.

### `apps/frontend`

```jsonc
"lib": ["ES2022", "DOM", "DOM.Iterable"],   // DOM.Iterable = for...of sobre NodeList, FormData…
"jsx": "react-jsx",                         // runtime automático: no hace falta `import React`
"noEmit": true                              // aquí TS solo comprueba tipos; el bundle lo hace el bundler
```

## Cómo verificar

**TypeScript todavía no está instalado en el monorepo**, así que los comandos de abajo
no se han podido ejecutar aún. Primero:

```bash
npm i -D typescript @types/node        # desde la raíz
```

Y después, lo más concluyente — pedirle a `tsc` la configuración ya resuelta, con la
herencia aplicada:

```bash
npx tsc -p apps/backend --showConfig
npx tsc -p apps/frontend --showConfig
```

Ahí deben aparecer las ocho banderas del base **dentro** de la config de cada app. Si
una no está, la herencia no se está aplicando. Para comprobar que el rigor funciona de
verdad, el mejor test es el ejemplo de dos líneas de arriba: debe dar
`'nombres[0]' is possibly 'undefined'`.

Type-check sin emitir nada:

```bash
npx tsc -p apps/frontend --noEmit
```

## Detalles a tener en cuenta

**`moduleResolution: "bundler"` en el backend es una decisión con filo.** Permite
imports sin extensión, pero si algún día ejecutas el `dist/` con `node dist/index.js`
tal cual, esos imports fallan en runtime: Node en ESM **sí** exige la extensión. Funciona
bien si el backend corre con `tsx` o se empaqueta con `tsup`. Si se prefiere Node a pelo,
el backend debe sobrescribir con `"moduleResolution": "NodeNext"` — es exactamente el
tipo de opción que un hijo tiene derecho a cambiar.

**Falta `packages/contrato`.** Necesitará su propio `tsconfig.json` extendiendo del
mismo base, y ahí sí conviene `"declaration": true` con `"composite": true`, porque es
el paquete que las dos apps consumen. Se hará al darle punto de entrada.

**No hay `references` de project references todavía.** Con tres workspaces pequeños no
compensa; el día que el `tsc` de todo el repo empiece a tardar, ese es el siguiente paso.
