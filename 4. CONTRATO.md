# Contrato en `tramitador` — esquemas OpenAPI del dominio

Primer paso del contrato: `packages/contrato/openapi.yaml` con los esquemas de
datos del dominio y **ninguna ruta todavía**. El objetivo es fijar el vocabulario
(qué es una solicitud, qué estados tiene, qué transiciones existen) antes de
discutir endpoints, para que backend y frontend hablen del mismo modelo.

## Qué hay

```
packages/contrato/openapi.yaml   -> OpenAPI 3.0.3, solo components/schemas
```

Ocho esquemas:

| Esquema | Tipo | Qué representa |
| --- | --- | --- |
| `Estado` | enum | `borrador`, `enviada`, `aprobada`, `rechazada` |
| `Accion` | enum | `enviar`, `aprobar`, `rechazar` |
| `Solicitud` | object | La entidad central de la bandeja |
| `NuevaSolicitud` | object | Lo mínimo para crear una: `tipo` + `solicitante` |
| `PeticionTransicion` | object | El cuerpo que dispara una transición: `accion` |
| `Tipo` | object | Entrada del catálogo externo de tipos |
| `Operador` | object | Quien gestiona la solicitud desde back-office |
| `Error` | object | `mensaje` obligatorio, `detalle` opcional |

La máquina de estados que modelan:

```
borrador --enviar--> enviada --aprobar--> aprobada
                             --rechazar-> rechazada
```

`aprobada` y `rechazada` son finales: no admiten más acciones. Nótese que el
contrato **no impide** por sí solo una transición inválida — `Accion` permite
cualquiera de los tres verbos. Quién puede hacer qué desde qué estado es una
regla de negocio que vive en el backend, no en el esquema.

## Los pasos que se siguieron

### 1. Leer la estructura que ya existía

`packages/contrato` ya estaba creado como workspace (ver `MONOREPO.md`), con un
`package.json` mínimo y sin contenido. El fichero se colocó ahí, no en la raíz ni
dentro de `apps/backend`, porque el contrato es precisamente lo que ambas apps
comparten.

### 2. Escribir `openapi.yaml`

Solo `components/schemas`. Tres detalles de la escritura que no son obvios:

**`paths: {}` vacío.** OpenAPI 3.0.3 exige las claves `openapi`, `info` y
`paths`. Sin las tres, cualquier validador rechaza el documento antes de mirar
los esquemas. Un `paths: {}` deja el fichero válido sin declarar ni un endpoint.

Conviene ser preciso con esto, porque "sin rutas" admite dos lecturas:

- *Sin endpoints definidos* — es lo que hay: `paths` está presente pero vacío,
  no declara ni una operación.
- *Sin que la clave `paths` aparezca siquiera* — eso **no es posible en 3.0.3**.
  Requeriría subir a **OpenAPI 3.1**, donde `paths` pasó a ser opcional.

Se descartó 3.1 deliberadamente: alinea el documento con JSON Schema 2020-12, y
eso **elimina `nullable`**. El `operador` nullable habría que reescribirlo como
`type: [string, "null"]`, y el soporte de herramientas para 3.1 sigue siendo peor
que para 3.0.3. Cambiar de versión es una línea, pero arrastra esa reescritura.

**`allOf` para los campos que referencian un enum.** En OpenAPI 3.0.3 (JSON
Schema Draft 4), cuando un `$ref` tiene claves hermanas, **las hermanas se
descartan**. Es decir, esto pierde la descripción:

```yaml
estado:
  $ref: '#/components/schemas/Estado'
  description: Estado actual de la solicitud.   # se ignora
```

Envolver el `$ref` en un `allOf` de un solo elemento lo arregla:

```yaml
estado:
  allOf:
    - $ref: '#/components/schemas/Estado'
  description: Estado actual de la solicitud.   # sí se conserva
```

(En OpenAPI 3.1 esto deja de hacer falta, porque las claves hermanas de un `$ref`
ya se respetan.)

**`nullable` y `required` a la vez.** `operador` está en la lista de `required`
**y** marcado `nullable: true`. No es contradictorio: en OpenAPI 3.0, `required`
significa "la clave está siempre presente" y `nullable` significa "su valor puede
ser `null`". Juntos dicen: el campo siempre viaja, con `null` cuando no hay
operador asignado. El cliente nunca tiene que distinguir entre "ausente" y "sin
asignar".

### 3. Verificar que parsea

No hay dependencias de negocio en el monorepo y `packages/contrato` no declara
ninguna, así que la validación se hizo con un `yaml` instalado fuera del
proyecto, en un directorio temporal, sin tocar `package.json` ni el lockfile.

## Cómo verificar

Sin añadir nada al repo ni tocar el lockfile, desde la raíz.

**1. Que el YAML parsea.** El CLI de `yaml` devuelve una lista de documentos por
defecto; `--single` fuerza a tratar el fichero como uno solo y falla si hubiera
más de uno:

```bash
npx --yes yaml@2 --single --json < packages/contrato/openapi.yaml > /dev/null && echo OK
```

**2. Que los `required` son los esperados.** Encadenando con `node`:

```bash
npx --yes yaml@2 --single --json < packages/contrato/openapi.yaml | node -e "
  const d = JSON.parse(require('fs').readFileSync(0,'utf8'));
  for (const [k,v] of Object.entries(d.components.schemas))
    console.log(k, v.enum ? '| enum: '+v.enum.join(',') : '| required: '+(v.required||[]).join(','));
"
```

Salida obtenida:

```
Estado | enum: borrador,enviada,aprobada,rechazada
Accion | enum: enviar,aprobar,rechazar
Solicitud | required: id,referencia,tipo,solicitante,estado,operador,creadaEn,actualizadaEn
NuevaSolicitud | required: tipo,solicitante
PeticionTransicion | required: accion
Tipo | required: id,nombre,descripcion
Operador | required: id,nombre
Error | required: mensaje
```

**3. Que es OpenAPI correcto.** Esto sí descarga un validador de verdad:

```bash
npx --yes @redocly/cli lint packages/contrato/openapi.yaml
```

Termina en `Validation failed with 1 error and 7 warnings`, y **eso es lo
esperado en esta fase**. Conviene saber qué dice cada cosa antes de intentar
"arreglarla":

| Aviso | Por qué aparece | Qué hacer |
| --- | --- | --- |
| `no-empty-servers` (el único *error*) | No hay bloque `servers` | Ignorar: aún no hay ningún servidor que declarar. Se añade con las rutas |
| `no-unused-components` ×6 | Ningún esquema está referenciado desde un `path` | Ignorar: es la consecuencia directa de no tener rutas |
| `info-license` | Falta `info.license` | Ignorar o añadir la licencia del proyecto |

Ninguno es una violación estructural del esquema OpenAPI 3.0.3: son reglas de
estilo de la configuración `recommended` de Redocly, que da por hecho un
documento terminado. Los seis primeros desaparecen solos en cuanto existan los
endpoints. Merece la pena volver a pasar el `lint` **después** de añadir las
rutas: ahí sí, cualquier error que quede será real.

## Decisiones tomadas que no estaban en el enunciado

Las ocho decisiones que no venían dadas, cada una con su veredicto tras una
revisión de diseño. Ninguna es difícil de cambiar **mientras no haya código
generado a partir del contrato**; a partir de ahí, cada una cuesta una migración.

### Sostenidas

| Decisión | Qué se eligió | Por qué se mantiene |
| --- | --- | --- |
| `operador` ausente | `required` + `nullable: true`: la clave viaja siempre, con `null` | Le ahorra al frontend distinguir *ausente* de *sin asignar* — en JavaScript `undefined` y `null` no se comportan igual, y esa diferencia genera errores en formularios |
| Objetos abiertos | Sin `additionalProperties: false` | Permite que el backend añada un campo sin romper clientes antiguos. Cerrarlos es decisión para cuando el contrato esté estable |
| `PeticionTransicion` | Objeto `{ accion }`, no el enum desnudo | Un objeto admite crecer; un `"aprobar"` suelto, no. Y es justo donde cabrá el motivo del rechazo |
| Fechas | UTC, ISO 8601, ejemplos con `Z` | Riesgo bajo y reversible |

`operador` es la que más parece un error a primera vista — `required` y `nullable`
suenan contradictorios — y es la que se defiende con más firmeza. En OpenAPI 3.0
significan cosas distintas: *la clave está siempre* y *su valor puede ser `null`*.

### A revisar

El `pattern` de `referencia` (`^SOL-\d{4}-\d{4}$`) es la decisión más débil de las
ocho: se dedujo de **un solo ejemplo**. Dos motivos para reconsiderarla:

- Fija en el contrato un techo de **9999 solicitudes al año**.
- `referencia` solo aparece en `Solicitud`, que es un esquema de **respuesta**. El
  `pattern` no valida nada que entre: solo restringe lo que el servidor puede
  emitir. Un cliente generado con validación estricta rechazaría una respuesta
  legítima el día que el formato cambie.

Recomendación: **quitarlo** y dejar el formato descrito en prosa, salvo
confirmación de que esa numeración es la definitiva.

### Pendientes de una decisión de negocio

| Decisión | Qué se eligió | Qué hay que resolver |
| --- | --- | --- |
| `solicitante` | `string` libre con el nombre del cliente | ¿Texto o entidad con id? |
| Forma de `tipo` y `operador` | Referencia plana: el `string` del id ajeno | ¿Quién resuelve el nombre legible? |
| `Solicitud.id` + `referencia` | uuid interno **y** código legible, ambos únicos | ¿Cuál va en la URL? |
| Tipo de `Tipo.id`, `Operador.id` | `string` libre (slug `alta-cuenta`, código `op-0042`) | ¿Lo impone el catálogo externo? |

**`solicitante` es la más importante de las cuatro**, y la asimetría salta al
revisar la lista entera: `tipo` tiene catálogo, `operador` tiene catálogo, y
`solicitante` — el **cliente**, la entidad de negocio más relevante de las tres —
es texto libre. Con un `string` no se puede buscar de forma fiable ni deduplicar,
y convertirlo después en un id es un cambio incompatible.

**`tipo` plano** significa que el listado devuelve `"tipo": "alta-cuenta"` y que
el frontend traduce a "Alta de cuenta" contra el catálogo de tipos. Es razonable
si ese catálogo es pequeño y cacheable, pero es una carga que se le impone al
frontend, y conviene asumirla a sabiendas.

**Los dos identificadores** no son un problema en sí, pero dejan una pregunta que
el contrato no responde: ¿la ruta será `/solicitudes/{id}` o
`/solicitudes/{referencia}`? Un operador que copia una referencia de un correo
espera lo segundo.

## Lo que el contrato todavía no dice

No son decisiones tomadas, sino **huecos**: cosas que el documento calla y que
habrá que resolver al definir las rutas.

**Nadie declara que una solicitud nace en `borrador`.** `NuevaSolicitud` no lleva
`estado`, lo que implica que lo fija el servidor. Hoy eso es una convención
tácita, no parte del contrato.

**El motivo del rechazo necesita dos sitios, y no existe ninguno.** Se respetó el
"no inventes campos" al pie de la letra, pero una bandeja real casi siempre
justifica un `rechazar`, y eso requiere:

- uno de **entrada**, en `PeticionTransicion` — el operador teclea el motivo al
  rechazar;
- uno de **salida**, en `Solicitud` — queda guardado y se muestra en la bandeja.

**`Error` no tiene código legible por máquina.** Solo `mensaje` y `detalle`, ambos
prosa en castellano. El frontend no puede ramificar por tipo de error sin parsear
texto. Para distinguir "transición inválida" de "solicitud no encontrada" o "sin
permiso" hará falta un `codigo`. Es la carencia más operativa de todas.

**La validación de transiciones no está en el contrato** (ya apuntado arriba: `Accion`
admite los tres verbos siempre). Lo que sí le corresponde al contrato es describir
el **error** que devuelve el backend al rechazar una transición imposible — y hoy
no puede hacerlo bien sin el `codigo` del punto anterior.

**No hay esquema de listado.** Al añadir las rutas habrá que decidir si
`GET /solicitudes` devuelve un array desnudo o un objeto paginado con metadatos.
Esa decisión pertenece al contrato, no al backend.

**El contrato aún no genera nada.** `packages/contrato` sigue sin `main` ni
`exports`, así que `import '@tramitador/contrato'` continúa fallando. El paso
natural siguiente es generar tipos TypeScript desde el YAML (`openapi-typescript`
o similar) y exponerlos por `exports`, para que backend y frontend compartan los
tipos y no solo el documento.
